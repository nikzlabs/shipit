req 7ShipIt owns the list; you own the keys. There is no “Add custom service” button anywhere on this screen — that is the point, not an omission. Both cards are ShipIt’s catalogue, split only by whether you have supplied a credential.
req 7Anthropic and OpenAI are ordinary rows. They sit in the same list as DeepSeek, with the same shape. Nothing marks them as the built-in or default choice.
req 5Auth type is a property of the service. The Subscription rows offer “Add account”; the API key rows offer a key field. This feature adds the key-authenticated ones — no row gains a new login flow.
req 10DeepSeek’s key mode shows no usage indicator at all — not an empty bar, not “n/a”. An API key has no allowance and nothing that resets, so there is nothing to render. Its subscription mode, one row up, does show one — which is why the indicator belongs to the billing mode rather than to the service.
req 5DeepSeek is one service with two billing modes. A subscription and an API key are not two services — same endpoints, same styles, one row — but they are not interchangeable either: the subscription includes only deepseek-v4-flash, while the key also sells deepseek-v4-pro, and one is metered where the other is not.
So each mode carries its own credential, its own model list, and its own usage indicator — a quota for the subscription, nothing for the key (req 10). Several subscriptions to one service would nest inside the subscription mode, since ShipIt routes between those itself (req 12).
req 6A service can speak two styles. DeepSeek shows both anthropic-messages and openai-responses; Fireworks shows one, which is why it can only ever appear under Codex.
Style tags appear here and nowhere else. They are the only visible explanation for why a service appears under one harness and not another, and that explanation is this screen’s whole purpose — the in-session picker shows model counts instead, since nobody chooses a harness on its wire format.

Harnesses

A harness is the agent CLI ShipIt spawns. Each speaks one API style, which decides the services it can drive. This deployment installed these two; the set is chosen when ShipIt is installed and changing it means redeploying, so there is nothing to add here.

Default. Follows whatever this install can run; pin one to stop it moving. Chosen independently of whatever a session is using.
req 6This screen is derived, not configured. Every cell comes from the catalogue joined against your credentials — style match, then per-model declaration. Nothing here is an editable field.
It exists so “why can’t I pick that model?” has an answer on screen rather than in a support thread.
req 6“DeepSeek contributes 1 of its 2” is the declaration doing visible work: speaking a style is necessary but not sufficient, and a model not declared for that style is simply absent rather than listed-and-broken.
req 14Two rows because this deployment installed two. Harnesses are not user-editable and the set is a property of the deployment, chosen at install from what ShipIt supports, Claude Code and Codex by default. A harness that was not installed is absent from this table and from the picker — not listed and empty.
Installed and credentialed are separate gates: no install, no models whatever your keys; installed, and you still only get the services you have a key for.
req 2Claude Code is listed while driving DeepSeek. Using a harness never requires an account with that harness’s own vendor — remove the Anthropic row from Services and this one still works.
req 9Background work names a service and a model, visible as its own setting. A default is fine; a hidden dependency is not — the failure this comes from was a lapsed subscription silently breaking session naming.
Which is why the default is a rule, not a model: unset resolves to the first model this install can actually run. A named default would be broken from day one on an install whose only credential is a DeepSeek key — the install this feature exists to make possible.

req 3One picker, one ordering rule. Every eligible model is listed the same way regardless of who provides it. A vendor’s own models get no separate surface and no privileged position.
req 8Ineligible models are absent, not greyed. The list is filtered to services with a credential. “Anthropic with no account” and “DeepSeek with no key” are the same condition and get the same treatment.
Entries are pairs, not model ids. The footer names the case that forces this: the same deepseek-v4-flash reachable through two services, at different prices. Persisting a bare model id cannot express which one you picked.
req 11Attribution says model, service and how it bills. Necessary because the model id alone is ambiguous, and because a retirement (req 13) can move a session onto a successor — this is where that becomes visible rather than silent.
req 4Switching is in-session. The picker changes the model without changing harness, so the session keeps its history and its container.
