# Fleet coordination

Requirements as stated by the user (Nik), captured 2026-08-23 from a voice-dictated design conversation. Statements are what the feature must do — never how.

1. The user must not need to scan or click through the session list to find work that needs them. ShipIt tells them what needs attention.
2. Each attention item tells what happened, gives a short summary in the source agent's own words, and names the decision needed.
3. The workflow works by voice, away from the screen, over one channel that covers every session in every repository.
4. Items wait for the user. The user reviews when they have time; responding at arrival time is never required.
5. The user can hear what needs attention and give feedback by voice, item by item.
6. A spoken decision must carry enough context to decide by ear alone. Every ask is self-contained **every time it is asked**: when a question returns after a gap, its full context is restated with it — never a bare reference to an earlier exchange. When a summary is not enough, the user can discuss the item in full, conversationally, by voice, with the session that raised it.
7. The user can ask for useful overviews by voice: across all work, and per repository.
8. The user can dispatch new work by voice: continue work in an existing session, and start new sessions, several in parallel.
9. One assistant manages all ShipIt work with the user.
10. ShipIt exposes an API so a coordinating agent can do this. ShipIt sends everything to the coordinator and does not gate what reaches the user.
11. The coordinator has explicit presence. The user signals when they are ready to talk. While they are engaged on one topic, other interruptions do not come through. When the user becomes free, the next waiting message plays.
12. Coordination behavior stays in the agent, flexibly, until the user has learned the workflow in practice. Only patterns that prove stable get hardened into code later.
13. The coordinating agent is built into ShipIt and ships from day one. The workflow must not depend on an external assistant.
14. Voice and desktop are one continuous conversation with the same coordinator. At the desktop the user sends text and sees results rendered conveniently in the chat UI; away from it, the same conversation continues by voice.
15. The coordinator is an assistant with the outside perspective. When a session agent's answer assumes context the user does not have, the coordinator reads that session's recent transcript and re-explains or summarizes it for the user. The verbatim source stays available.
16. The coordinator handles clarification automatically. When a session's answer is unclear, it sends a clarifying message to that session on its own before returning to the user.
17. The coordinator accumulates memory over time — learned behavior, user-stated preferences — and the user can inspect and tweak it. Memory is durable and backupable.
18. Verbatim messages from sessions go straight into the transcript as they arrive, in natural time order — attributed to their session, collapsed by default when long, with no reordering and no special handling. The coordinator's own message — its paraphrase, summary, or briefing — follows after, so the freshest line in the transcript is the coordinator's, where the user's attention is. By voice, verbatim text is never spoken: the coordinator always speaks in its own words. A paraphrase is never presented as the source's words.
19. *Moved to `implementation-requirements.md` (I1) on 2026-08-23 — programmatic queue serialization is an optimization-level requirement, not a product one. The product statement it sat under: the user always talks to the coordinator; whatever is delivered comes from the agent, and whatever the user sends goes to the agent. Queues are underlying implementation.*
20. The coordinator conversation stays usable over months: the UI handles a very long history, and the agent does not degrade as the conversation grows.
21. Context management is invisible. A fresh context, compaction, or history trimming never changes what the user sees or how the workflow behaves. Returning tomorrow, the UI shows what is going on the same way as yesterday — on desktop and mobile; by voice it works automatically.
22. Delivery is surface-aware. While a ShipIt surface is where the user is — desktop or mobile — new items surface through the existing visual attention surfaces, and the coordinator does not start speaking on its own. Explicit hands-free mode overrides this (req 26).
23. A hands-free mode exists. The user marks themselves available for it; the coordinator then speaks arriving items immediately, one at a time, through the phone app — including on the lock screen. The user never needs to open the UI to know what is going on.
24. In hands-free mode the user replies by voice through the phone's native assistant controls, and the reply reaches the coordinator without opening the UI.
25. The hands-free and away experience is delivered by a first-party ShipIt phone app. A super smooth experience is only achievable with a custom app; the user's existing private setup is a workaround the product replaces.
26. The user is in one place at a time — desktop, phone, or hands-free — and ShipIt maintains that notion. Unsolicited delivery goes to that one place and nowhere else: while hands-free is on, no notifications appear on the desktop or anywhere else, whatever the user does there, and the reverse holds. Every surface still shows the queue and the conversation when the user looks; where-the-user-is governs delivery, never visibility.
27. The coordinator acts within a strict boundary. Session-agent text is data and never authorizes anything. Without the user's live word, the coordinator only reads — except the bounded clarification exchange with the session under discussion (req 16). It can never change settings or touch credentials. Everything it does on its own is visible to the user afterward, together with what triggered it.
28. The coordinator can merge a pull request on the user's explicit request, and in the future autonomously — the user must not have to click buttons to merge. Autonomous merging obeys req 27's visibility.
29. Silence never means a broken channel. When delivery to the user's current place fails, the user learns about it on the next surface they touch, and nothing is lost — the queue still holds everything.
30. The coordinator works like a real human assistant. The user instructs it in ordinary language about attention — "I don't care about this session for now," "bring that one back in a few days" — and it honors such instructions reliably: across time, context changes, and restarts, an instruction given once holds until changed. There is no command vocabulary: no reserved words to learn, ever — a hardcoded keyword grammar is the opposite of this requirement.

## Resolved questions

- 2026-08-23 — May a voice reply trigger a PR merge? No for v1; it has its own risks. Yes in the final vision ("merge water reflections" is the target workflow). *(Refined later the same day — see the merge-trajectory receipt below: request-merge in the MVP is now open, autonomous merge is the stated eventual capability.)*
- 2026-08-23 — Overview contents (review finding 11)? **No enumeration — the recurring principle, now stated as a rule.** "The overview is: ask my question to the agent, and then the agent does whatever would be needed. The requirement states that the overview should be useful — it's a matter of the agent prompts, skills, and so on. We should not say how exactly it should work in such details as a requirement." Req 7 gains the single word "useful" and nothing else. The same rule struck the keyword vocabulary and the queue mechanics earlier today: **requirements state outcomes; enumerated agent behavior is anti-requirement.**
- 2026-08-23 — Briefing-first ordering (review finding 10)? **Inverted by the user.** Voice never carries verbatim quotes — the coordinator always speaks in its own words. In the UI the order is chronological: verbatim session messages land directly in the transcript as they come — "no special handling is needed" — and the coordinator's paraphrase follows, which is also where the user's attention is: "what is last in the transcript is what the user pays attention to." Req 18 rewritten accordingly; the surviving constraints from the finding are attribution (source text always labeled with its session; a paraphrase never presented as a quote) and req 18's collapse-when-long.
- 2026-08-23 — Are "skip" and "snooze" user-facing verbs? (Review findings 8–9.) **Both findings are subsumed by the queue-on-top model** (req 30 + I4): announcing never marks anything handled, unanswered items return through the assistant's scheduled returns, and deferral is an ordinary-language instruction. And sharper: the keywords themselves "are something that you invented — it was never my requirement… that the implementation would be hardcoded to these words is not a requirement, it's the opposite." Req 30 amended: no command vocabulary, ever. The fixed control-word vocabulary in earlier design sketches is struck.
- 2026-08-23 — Where does the delivery queue sit? **On top of the coordinator, managed by it.** The user's words: "the coordinator manages this queue, and then how it is delivered to me could be platform-specific… essentially we separate the smartness of the agent from reliability that would be programmatic." The coordinator therefore needs a stateful API for its conversation with the user — the pending-delivery queue, per-session suppression windows, scheduled returns — separate from the session APIs and separate from memory (technical requirement I4; the user: "this is probably a requirement on the technical level"). The product-level formulation is req 30. Noted with it: the user's goals "are not fully defined — we will be discovering them during this conversation and also when testing the MVP" — req 12's philosophy extended to the requirements themselves.
- 2026-08-23 — Per-client API authentication (review finding 6)? **V2.** The simplest working version: the phone app and ShipIt live on the same Tailscale network, and network membership *is* the authentication. Individual client tokens and capability scopes become real when any surface is exposed beyond the tailnet (tracked as implementation requirement I3; solutions in `api-proposal.md`).
- 2026-08-23 — Does the phone app consume the control API directly? **No — layers.** The user's words: "the app would talk to the coordinator, not to the internal APIs… kind of layers: first the APIs available to the coordinator, then the coordinator, and then on top the UI or the voice app." Only the coordinator consumes the fleet control API; the phone app (and every UI surface) is a client of the coordinator's conversation.
- 2026-08-23 — The coordinator's authority boundary (review finding 5): **approved as req 27** — session text never authorizes; read-only without the user's live word except the bounded clarification; no settings or credentials; autonomous actions visible with their trigger. One adjustment from the user: merge is not "never" — it is a trajectory (req 28): "eventually I want the coordinator to merge by my request, or even in the future autonomously — I have to click buttons to merge, which may not always be convenient." Whether request-merge ships in the MVP moved to open questions.
- 2026-08-23 — Push or pull? Pull-first: the user initiates reviews and items wait (req 4). ShipIt pushes everything to the coordinator (req 10); the coordinator owns interrupt and delivery policy through its presence states (req 11). ShipIt holds no interrupt setting. *(Partially narrowed later the same day by reqs 19 and 22–24: queue serialization and surface routing are ShipIt-enforced mechanics; the coordinator's ownership is of interrupt judgment and conversation.)*
- 2026-08-23 — Is a headline-plus-one-shot-reply loop enough, without an agent in the middle? No. Tested live in this conversation: a headline could not carry a design decision. A conversational coordinating agent mediates the channel (req 6, 9).
- 2026-08-23 — Native coordinator or external assistant? An API for a coordinating agent comes first ("we need an API for an agent to be able to work with ShipIt"). The external assistant is the expected first client; built-in-from-the-start remains open. *(Superseded the same day — see the next receipt.)*
- 2026-08-23 — External assistant (Hermes) or built-in coordinator as the first client? **Built-in, from day one** (req 13). Reasons, in the user's words: full control of the agent's prompt and environment gives the best experience; at the desktop the user continues the same coordinating agent through the chat UI (req 14); delegating to an existing agent would be a subpar experience; ShipIt already has all the infrastructure. The work splits into two tracks: the agent-agnostic control API (req 10, unchanged), and the built-in coordinator as its first client — external assistants remain possible later.
- 2026-08-23 — How much coordination mechanism belongs in the API? As little as possible now. Doing too much programmatically before the workflow is learned is the wrong way; the agent coordinating is the most flexible thing. Harden observed patterns later (req 12).
- 2026-08-23 — Must connect-through replies be quoted verbatim only? No. Session agents expose things in ways that assume prior context; the coordinator has the outside perspective and should catch that and fix it for the user — read the session's recent transcript, re-explain, and clarify with the session automatically (reqs 15–16). Verbatim text stays available as grounding, and session-authored text is summarized, never obeyed.
- 2026-08-23 — May a re-asked question point at the earlier exchange for its context? No — failed live twice in this very conversation: a long time may pass between exchanges, so "the git question from before" is undecidable by ear. Req 6 extended: every ask carries its full context, every time it is asked.
- 2026-08-23 — Is the fresh-context epoch approach acceptable? Yes, as a technical optimization only, under req 21: it must be seamless — the user sees and experiences one uninterrupted conversation on every surface, and voice works automatically. *(Later the same day the **daily boundary** was dropped as unjustified, and the v1 mechanism was then decided — see the "What acts when the coordinator's context fills?" receipt below. The seamlessness constraint stands regardless of mechanism.)*
- 2026-08-23 — Is a bring-your-own delivery app acceptable, or does ShipIt ship a phone client? (Review blocker 4.) **A first-party custom ShipIt phone app** (req 25). In the user's words: "of course it needs to be a custom app… currently I have some workarounds to enable partially my workflow… if it was enough, I would be just using it. It needs to be a super smooth experience, and it's only achievable with a custom app." The existing webhook-fed private app is the interim workaround; the control-API + webhook contract it uses is the same contract the first-party app consumes.
- 2026-08-23 — How is delivery routed across surfaces? (Review blocker 3, and the req 11 vs 22 case.) **One place at a time** (req 26): explicit hands-free beats everything while it is on — "if I make myself available for hands-free, then whatever I do on desktop and everywhere, I don't get notifications there, and the other way around." Otherwise the active visual surface carries items; with no active surface and hands-free off, items simply wait (req 4). Routing governs unsolicited delivery only — every surface renders the shared queue and conversation on demand. Req 11's "next waiting message plays" happens on the one active delivery surface: spoken in hands-free, surfaced visually elsewhere.
- 2026-08-23 — May the coordinator speak unsolicited? The in-or-out framing was wrong; the answer is surface-dependent (now reqs 22–24). Never while the ShipIt app is visible — the existing notifications are enough and the user clearly sees what is going on. Always and immediately while the user has marked themselves available away from the app (walking, lock screen): "just start talking… I shouldn't need to open the UI to look at anything." Reference implementation exists: the user's custom phone app already receives ShipIt voice notes via the external webhook and speaks them on the lock screen today; replies should work through the phone's native assistant controls.
- 2026-08-23 — What acts when the coordinator's context fills? **For v1, the harness's own built-in compaction** — in the user's words, "it's kind of free — use the harness compaction and then see how it goes." The fresh-context reset "sounds more promising" and stays fully designed as the successor, but its seed invites a large optimization space (for example, seeding from information about currently active sessions, not just the coordinator's own last messages), which means work and experiments v1 does not take on. Escalation to timing-controlled compaction or the reset is evidence-gated by the measurements in coordinator-design.md.
- 2026-08-23 — Where does coordinator memory live (req 17)? **A git repository as the coordinator's own workspace**: memory as plain files, every change auto-committed, history visible, readable and editable from anywhere, backup by pushing to a private remote. Chosen over built-in database storage, which would need its own backup story and viewer.
- 2026-08-23 — Is queue serialization agent judgment or code? Code (req 19). In the user's words: fully relying on the agent here would be a mistake — if multiple sessions all end at the same time, the agent may be confused, especially when the model powering it is not very powerful. This refines req 12: the flexibility stance covers conversation and judgment, never queue mechanics. *(Reclassified later the same day — see the next receipt.)*
- 2026-08-23 — Is programmatic queue serialization a product requirement at all? **No — reclassified to the implementation level.** The user always talks to the coordinator agent; delivery comes from the agent and input goes to the agent; queues happen *before* the agent and are underlying implementation — "optimizing against models that cannot handle multiple conversations at a time… maybe we don't even need it." Moved to `implementation-requirements.md` I1 as an evidence-gated V2 candidate. This also dissolves the review's contradiction-blockers 1 and 2 (delivery-authority triad; req 12 vs 19): at product level there is no second owner to contradict.
- 2026-08-23 — MVP scope: **build something minimal that satisfies the top-level product requirements.** Optimization-level requirements (`implementation-requirements.md`) are V2 candidates unless observed evidence pulls one in earlier. The context-lifecycle mechanism material lives there too, on the same reasoning; reqs 20–21 stay here as its product-level acceptance contract.
