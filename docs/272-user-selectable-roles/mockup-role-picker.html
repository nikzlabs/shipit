What the real row changed. The four labelled controls live in a min-w-0 overflow-hidden group whose labels are sacrificed when the row runs out of width, so that Send is never carried off the edge (docs/260 req 1, req 8; MessageInput.tsx — wide-row-clip-group). Every character added inside that group is spent from a budget that is already contested and already clips between 700 and ~808px. Appending to the model label (option b) makes the single widest label wider, so the group starts clipping sooner and clips a compound label whose two halves are not equally important.

Why option a instead. A separate label can be given a separate priority. The role name is the one label in the group that is redundant — the menu it came from names it too — so it should be the first to shrink to its marker and the last to matter. That is a rule the clip group can express and a compound label cannot.

Still worth your judgement: option a puts a read-only label among four controls that open menus. It is the only thing in that group that does nothing when clicked. The alternative is to accept option b's clipping, or to show the role only inside the menu and nowhere on the row — which would not satisfy req 13.

Roles sit above the models, in the menu that is already there. Selecting one writes the harness, service, billing mode, model and reasoning level at once — the rows below then show that model as selected. Selecting a plain model clears the role label, because the combination is no longer the role's.

Unavailable roles stay, and say why (req 9). They cannot be selected, and carry the reason and the fix. The reviewer role is absent (req 10) — this list is the whole reason that question mattered.

"No role" is not a fifth state. It clears the label only. It does not change the harness, model or reasoning: nothing is put back (req 3).

The open question, shown: if two roles carry identical parameters, this prototype marks the first by name and stays silent about the other.

The Role panel.

This is where the design does grow. docs/260 states the root list stays four rows however far the catalogue grows. That promise is about catalogue growth, and this adds a row for a new kind of setting rather than for more models — but it is still a cost, and worth naming before it is built.

The alternative, if five rows is too many: fold Role into the Model row (Model · Deep dive) and put roles at the top of the Model panel, as the wide menu does. One rule at both widths, but a row labelled "Model" would then also set the harness and reasoning.
