## Why a real container, and evidence this one is fresh

A dogfood run cannot settle this. `docker/Dockerfile.dev` creates **no `.grok`
symlink at all**, so the dangling-link cause cannot exist there — which is
exactly why the two green dogfood runs of 2026-08-18 coexisted with a dead
outer consult. A dogfood-only proof is not proof, so every observation below
comes from a real session-worker container.

This session's container is post-redeploy:

| Signal | Value |
|---|---|
| `/usr/local/bin/grok` symlink mtime | `Aug 19 12:42` |
| `~/.grok` symlink mtime | `Aug 19 12:43` |
| Container start | `Aug 19 13:08` |
| Fix commit `aa79014b` authored | `2026-08-19 13:44:54 +0200` (= 11:44Z) |

The image layers postdate the fix commit, and the container postdates the
layers.

## Part 1 — the planning#444 fix, three checks

### Check 1 — a grok-pinned session turn completes

The pre-fix symptom was a first turn ending `error`, subtype
`error_during_execution`, `duration_ms: 0`, no stream events — reproduced
before the fix on probe session `3c992d1a…`.

A grok-pinned child session was created for this run:

```
shipit session create --role Grok --title "Grok outbound consult probe"
→ session-id: c57755ea-5496-42d9-b229-d993472e259d, branch shipit/ietggr
```

`shipit session view … --json` reports the **orchestrator-resolved** backend
(not the model's self-report): `"agent":"grok"`, `"model":"grok-4.6"`,
`"originRoleName":"Grok"`. That session ran a multi-step first turn to
completion (`status: idle`, no error), then a **second** turn on a follow-up
message, also to completion. Its own statement: *"This session's first turn
completed normally."* **PASS.**

### Check 2 — `command -v grok` resolves to the direct binary

Measured in two independent containers, and in both cases *from inside a grok
spawn* rather than from a shell alongside it:

```
/usr/local/bin/grok
```

`/usr/local/bin/grok` is a symlink to
`/opt/agent-cli/node_modules/@xai-official/grok-linux-x64/bin/grok` — the
decompressed platform binary. The launcher shim
`/opt/agent-cli/node_modules/.bin/grok` **no longer exists**
(`ls: cannot access … No such file or directory`), and `which -a grok` returns
exactly one path. This holds despite `PATH` still placing
`/opt/agent-cli/node_modules/.bin` ahead of `/usr/local/bin`, because there is
no longer anything for it to find there. **PASS.**

### Check 3 — the per-turn `GROK_HOME` carries no `bin/` payload

The npm launcher, had it run, would bootstrap the ~157 MB platform payload into
`$GROK_HOME/bin` **once per turn**. Three spawn roots were observed across two
containers:

| Spawn root | Container | `du -sm` | `bin/` |
|---|---|---|---|
| `/tmp/grok-home-DUp1w8` | this session (INBOUND consult) | 1 MB | `BIN ABSENT` |
| `/tmp/grok-home-pGwgId` | child session `c57755ea…` | 1 MB | `BIN ABSENT` |
| `/tmp/grok-home-pZhx3A` | this session (role-less target) | 1 MB | `BIN ABSENT` |

Two measurements, deliberately independent:

- **In-band**, by the grok CLI itself inside its own spawn:
  `test -e "$GROK_HOME/bin" && echo "BIN PRESENT" || echo "BIN ABSENT"` → `BIN ABSENT`.
- **Out-of-band**, by an external 5 Hz watcher running in this container across
  the whole spawn lifetime, blind to what the CLI reports. It saw both of this
  container's spawn roots (`DUp1w8`, `pZhx3A`) and **every one of its 69 samples
  reads `size=1MB bin=no`** — the payload never appears, even transiently.

Each root is also short-lived: both were gone from `/tmp` after their turn, so
the throwaway-root contract holds as well.

**PASS.**

### A fourth observation — the root cause is fixed, not merely survived

Worth separating, because the planning#444 fix has three layers and only one of
them is a *fallback*. Both observed spawn homes contain:

```
lrwxrwxrwx  sessions -> /home/shipit/.grok/sessions
```

A **symlink**, which is the success path of `makeSpawnHome`. Had the shared root
still been unusable, the adapter's resilience layer would have degraded to a
self-contained root with a **local `sessions/` directory** and narrated a
warning to the transcript. Neither appeared. Correspondingly,
`/credentials/.grok` now exists as a real directory (mode 0755, owned
`shipit:shipit`) containing `sessions/`, and `~/.grok` resolves through it.

So the entrypoint/provisioning layers did their job and the adapter's fallback
was never needed — the two are not being conflated here.

## Part 2 — `shipit agent run`, both directions

### INBOUND — Claude parent → grok sub-agent: **PASS**

`shipit agent run --role Grok --prompt-file -`, backgrounded and collected with
`shipit agent result`.

```json
{"spawnId":"eb61663c-1b3e-4f72-9d00-656376c3ae67","subAgentId":"grok",
 "roleName":"Grok","runOn":{"serviceId":"xai","billingMode":"key","modelId":"grok-4.6"},
 "status":"success","durationMs":13283,"costUsd":0.061874,
 "truncated":false,"outcome":"finished"}
```

Both halves of the contract now hold. **Routing** was already correct in the
previous run (`subAgentId: grok`, the `xai:key grok-4.6` route). What is new is
that the **process** half completes: `status: success` rather than `error`,
`durationMs: 13283` rather than `0`, `costUsd: 0.061874` rather than `0`, and
real output rather than none. The consult ran shell commands, read
`/workspace/README.md`, correctly named its first heading (`ShipIt`), and
emitted the requested `PROBE-OK` token.

### OUTBOUND — grok parent → another harness: **PASS**

The defined form is unchanged: a one-shot sub-agent cannot itself spawn
(`/shipit-docs/agent.md` — "No recursion"), so the only grok-parent context
`shipit agent run` can be exercised from is a **grok-pinned session**. That is
child session `c57755ea…` above.

From inside that grok context:

```
shipit agent run --role Fable --prompt-file -
→ RUN-ID: 47b49de6-8cc7-43c3-9d4a-6ac453c05461
→ EXIT_CODE: 0
→ output: OUTBOUND-OK
```

The sub-agent's credentials arrived over the brokered path — the grok container
holds no Anthropic credential of its own, and the consult would have failed 401
had `shipit agent run` not supplied them server-side.

This direction was **not reached at all** in the previous run (the spawn cap was
consumed by inbound retries), and its outcome was recorded there only as a
prediction of failure. That prediction is now superseded by the fix.

### Role-less fully-specified target (docs/275, optional): **PASS**

```
shipit agent run --agent grok --service xai --billing-mode key --model grok-4.6
```

with **no `--effort`** — docs/275's motivating acceptance case for a harness
that declares no reasoning levels, and the case the previous run could not
exercise because the cap check runs before target resolution.

```json
{"spawnId":"96b99b49-3c6d-4424-8a94-f8fda6f0f1f0","subAgentId":"grok",
```

The four identity flags resolve to a complete grok target and the run succeeds

role-less call, and the field that distinguishes this path from the inbound one
above.

## Spawn budget

`SUB_AGENT_PER_TURN_CAP = 3`, shared with `shipit session create`. This run
spent exactly three in one turn — INBOUND consult, the grok-pinned child
session, and the role-less target — with no retry needed, following the rerun
order the previous run's doc laid down. The child session's own outbound consult
draws on the **child's** per-turn budget, not the parent's, which is what made
one turn sufficient.
