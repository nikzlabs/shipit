# Run — Antigravity 1.1.27 (2026-09-14)

The full recipe for a new harness, run once the saved `GEMINI_API_KEY` became
billable. It is the first exercise of the recipe that **found a shipping
blocker**: the merged harness could not read or write the user's repository at
all. Three defects in total, all fixed on the branch that carries this record.

The captures are vendored beside the harness's own probes, in
[docs/301-antigravity-harness/probes/](../../301-antigravity-harness/probes/),
because they double as that integration's evidence; `review-probe.sh` there
reproduces ShipIt's exact spawn argv.

## Step 1 — capture

The recipe's tour prompt ([`tour-prompt.txt`](../../301-antigravity-harness/probes/tour-prompt.txt)),
one turn, the pinned binary, ShipIt's own argv, prompt on stdin as a
`stream-json` user frame. Two captures, because the first one failed:

| Capture | Spawn | Outcome |
|---|---|---|
| [`tour-no-add-dir.ndjson`](../../301-antigravity-harness/probes/tour-no-add-dir.ndjson) | as the merged adapter spawns | exit 0, but every file tool addressed `$HOME` |
| [`tour2.ndjson`](../../301-antigravity-harness/probes/tour2.ndjson) | `+ --add-dir <repo>` | exit 0, every file tool addressed the repository |

## Step 2 — inventory

**Event vocabulary (Layer A).** `init`, `step_update`, `result` — no new event
type, nothing that would reach a `default`. Step types: `user_input`,
`agent_response`, `tool` — a subset of the five declared.

**Step states — one finding.** The declared union was `ACTIVE | DONE`. The
captures carry **`ERROR`**, twice, whenever the CLI rejects a tool's arguments
(`invalid arguments: at '/WaitMsBeforeAsync': got string, want integer`). No
1.2.2 capture contained a failed tool, which is why it was never declared.

**Tool names (Layer B).** `init.tools` offers **57**; `ANTIGRAVITY_TOOL_NAMES`
declares **57**; the two sets are equal, with no drift on this version. Observed
in the tours: `write_to_file`, `replace_file_content`, `view_file`,
`find_by_name`, `grep_search`, `list_dir`, `run_command`, `manage_task`. Every
one is declared, and every one but `manage_task` is in the normalizer's table —
which is deliberate, since `manage_task` manages background processes rather
than a to-do list.

**Input keys — one finding.** Diffing every observed parameter key against
`INPUT_KEY_RENAMES` left two unmapped, and each is the single field its card
exists to show: `grep_search` sends **`SearchPath`** (not `SearchDirectory`) and
`find_by_name` sends **`Pattern`** (not `Query`). The Grep card rendered with no
path and the Glob card with no pattern.

**Surfaces with no observed driver.** The **task panel** has none, and this is
structural rather than drift: none of the 57 tools is a to-do tool, and the model
keeps its to-do list as prose in the transcript and as a `todo.md` inside the
CLI's own `brain/` directory. Nothing in ShipIt is waiting for a driver that
disappeared.

## Findings

### 1. The CLI's tools run under `$HOME`, not the spawn cwd — SHIPPING BLOCKER

`init.cwd` echoes the spawn cwd, so the stream looks correct. The tools do not
follow it. Without `--add-dir`, `run_command`'s own `pwd` prints `$HOME`,
`view_file` on the repository's `package.json` ends `ERROR` because it looked
under the home, `grep_search` and `find_by_name` take the home as their search
root, and `probe-note.md` is written into the home. With `--add-dir <repo>` every
one of them addresses the repository. The minimal pair is
[`pwd-probe.ndjson`](../../301-antigravity-harness/probes/pwd-probe.ndjson) and
[`adddir.ndjson`](../../301-antigravity-harness/probes/adddir.ndjson).

This was invisible in production for the worst possible reason: the adapter sets
`HOME` to a **fresh `/tmp` directory per spawn**, so an Antigravity turn read and
wrote an empty scratch home and left the repository untouched — while exiting 0
and reporting success. **Fix:** the adapter passes `--add-dir params.cwd`.

### 2. A failed tool step was dropped entirely — Layer A

`handleToolStep` treated only `DONE` as terminal, so an `ERROR` step fell into
the ACTIVE branch and returned on the already-registered index. The call got no
`agent_tool_result` at all: the tool card stayed "running" for the rest of the
session, the CLI's own error text never reached the user, and the id leaked.
**Fix:** `ERROR` is terminal too, and emits a result carrying
`tool_info.error.message` with `is_error: true`.

### 3. Two search fields no card could read — Layer B

**Fix:** `SearchPath → path` and `Pattern → pattern` in `INPUT_KEY_RENAMES`.

## Step 3 — conformance

Guards added to `session/agents/antigravity/adapter.test.ts` and
`antigravity-tool-normalizer.test.ts`, each proved red by reverting its own fix
alone. Two of them are byte-shaped replays of the committed captures rather than

## Step 4 — live recognition run

The dogfood inner instance, Antigravity on `google/key`, `gemini-3.1-pro-preview`,
against `nicolasalt-shipit/todo-list`. Asserted on **persisted history**, not on
the live stream. The matrix, as it landed:

| Surface | CLI tool | Transcript |
|---|---|---|
| File read | `view_file` | `Read`, `file_path` in the session workspace, result `21 lines, 420 bytes` |
| File write | `write_to_file` | `Write`, correct `file_path` |
| File edit | `replace_file_content` | `Edit`, correct `file_path` |
| Shell | `run_command` | `Bash`, `command`, stdout `conversion-probe` |
| Search | `grep_search` | `Grep` |
| Directory | `list_dir` | `Glob`, real listing |
| Task list | — | no driver (see above) |

The turn ended cleanly with its final message persisted and `inProgress` cleared,
and `probe-note.md` landed inside the session's own workspace — the end-to-end
confirmation of finding 1 through ShipIt's own adapter.

**A known limitation, not a defect of this branch:** `write_to_file` and
`replace_file_content` send only `TargetFile` in `tool_info.parameters`. The CLI
never puts the body, the old text or the new text on the stream, so Write and
Edit cards render with a path and an empty body, and no diff. The
`CodeContent` / `TargetContent` / `ReplacementContent` renames stay in the table
against a future version that sends them; on 1.1.27 they match nothing.

**Interactive surfaces.** `ask_question`, `ask_permission` and
`ask_custom_permission` are offered in `init.tools` and are deliberately left
out of the normalizer's table, because their input shapes had never been
observed. They still have not been, and now for a measured reason: told
explicitly to use `ask_question` and to ask before writing any code, the CLI in
`--print` mode does not call it — it `echo`s the question and then asks in prose
([`ask-question.ndjson`](../../301-antigravity-harness/probes/ask-question.ndjson)).
`ask_permission` cannot fire at all, since the harness is full-auto only (req 8).
So the named exclusion is correct, and nothing headless can drive those surfaces.

**The negative control is weaker than the recipe asks for.** The vocabulary
guard (`only maps names the CLI actually offers`) compares two constants — it
would not catch a fabricated name arriving in a captured event, which is what the
recipe's control is for. What this run does have is an unplanned control of a
different kind, and a sharp one: the first tour was an exit-0, `SUCCESS` turn
whose text claimed all seven steps were done with **none** of them done in the
repository. It is evidence that a green stream proves nothing about effect; it is
not a check against the checker.

## What this run did NOT cover

- **The subagent surface has no observed driver.** The tour's step 7 asks for a
  subagent; in both tours the model satisfied it with a shell command instead, so
  `invoke_subagent` / `define_subagent` / `browser_subagent` — all offered in
  `init.tools` and all mapped to `Agent` — remain unexercised. Their event shape
  and their result shape are unverified.
- **Step 4's UI half.** The matrix was asserted on persisted history read back
  over `GET /history`, which is the durable surface; the recipe also asks for a
  UI snapshot and a reload-and-re-snapshot, and neither was taken.
- **ACCOUNT mode**, below.
