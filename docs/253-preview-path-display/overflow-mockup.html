Preview toolbar overflow on narrow panels

PreviewToolbar.tsx is one non-wrapping flex row with no breakpoints. The right group is shrink-0, the left group has no min-w-0, so when space runs out the path collapses to zero and then the row simply clips. Below are five ways to fix it, each live at the width you set. Drag the slider — the measured options re-collapse as you go.

Measured in this mockup: the bar needs ≈520 px to lay out without clipping. That is wider than every phone, so mobile always breaks — but it is also wider than a desktop split pane dragged past halfway, which is why this is not only a mobile bug.

What I would build: A, then B underneath it, driven by a container query

The address outranks every label, and it degrades by shrinking rather than by disappearing. Labels are a fixed cost that buys nothing once you know where you are; the address is the only thing in this bar that changes as you use the preview. So labels convert to icons first — each one handing its width straight to the address — and only when they are all gone does the address start truncating.

A and B are then stages of one mechanism, not rivals: drop labels, shrink the address, and only demote controls into the kebab if it still does not fit. Nothing ever becomes unreachable at any width.

  1. Never leave slack beside a truncated address. If the address is cut short, every remaining pixel in its region belongs to it. That falls out of making the chip content-sized and shrinkable (flex 0 1 auto, min-w-0) instead of hiding it at a breakpoint — a hidden address leaves a visible gap, which is the tell that the layout gave up early.
  2. The copy icon is a hard floor, not a shrink-0. Today it is already shrink-0 (PreviewPath.tsx:77) and that is not enough — it lives inside a flex-1 min-w-0 region that collapses to zero, so it is clipped away with the text it belongs to. The region needs a min-w of one icon button. In every option above, copy survives down to 220 px.
  3. Measure the panel, not the viewport. The preview is a split pane on desktop, so it overflows at desktop widths too. useIsMobile() would miss that; a ResizeObserver or @container on the toolbar catches both. IssuesViewer.tsx already uses container queries for the same reason.
  4. Fix the flex bug regardless. The left group needs min-w-0 and the service label needs truncate. That alone converts a clip into a graceful squeeze, and it is a two-class change worth landing whichever option wins.
  5. Reuse, don't invent. useTabLabelCollapse.ts is the measuring stage and ui/overflow-menu.tsx is the demotion stage — both already shipped and tested. The query already shrinks before the route (shrink-[999]), so the last step of A is free.
  6. The address minimum is the one number to agree on. It is the whole tuning surface: it decides how early labels start going. The second slider above is there to settle it by eye rather than by argument — at a 130 px minimum the first label goes at ≈676 px, which is roughly a half-width split pane.

E is the better product if the toolbar is going to keep growing; at ≈288 px it fits every phone with nothing collapsed, and it is the only option whose layout is stable across widths. It is worth doing on its own terms, not as an overflow fix. D I would not ship — suppressing the scrollbar makes a clipped bar look like a complete one, which is the bug we are fixing.
