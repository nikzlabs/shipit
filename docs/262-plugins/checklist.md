Next design slice (server mechanics):

- [x] Checkout mechanics: bare-cache reuse (serialized per cache), per-generation checkout in the session state dir (req 2). **Correction (2026-08-13):** an earlier version of this item said the generation directory IS the writable layer and the CoW layer "buys nothing". Req 7 says install output lives somewhere that is neither plugin source nor project data, so the checkout stays pristine and the CoW layer is back — it buys exactly that requirement
- [x] Mounts (agent container half): the session's plugin root mounted **read-only** at `/plugin-store`, with `/plugins/<name>` a container-side symlink through it, so a generation swap is visible without recreating the container (reqs 2, 7). The store-not-generation shape is settled and reviewer-confirmed (Docker resolves a bind source's symlinks at creation, so a per-generation mount would pin one generation); the writable twin in PR #2202 is **withdrawn** — the agent container gets no writable view at any path. `/project` for services lands with the compose work (req 21)
- [x] Generation staging/activation: stage → validate (incl. phase-2 selectors) → atomic symlink swap; the record lives inside the generation so reads are atomic; failure keeps the prior generation whole and live; a per-repo serial QUEUE (not promise-joining, so a mid-flight declaration edit is never lost); prune never deletes the live generation (reqs 12, 13, 14, 15). Service prepare/recreate lands with the compose work
- [x] Per-plugin per-session shared state directory + validated settings file (reqs 17, 18, 26) — `orchestrator/plugin-state.ts` owns the on-disk layout, `shared/plugin-contract.ts` fixes the names both surfaces use (`SHIPIT_PLUGIN_STATE`, `SHIPIT_SETTINGS`, and the container mount points). The state dir deliberately sits OUTSIDE `<sessionDir>/state/`: that subtree is in `REGENERABLE_SESSION_SUBDIRS` and is deleted by disk-tier eviction, while req 18 says this data survives everything short of a session reset. Keyed by `alias`, so two `use:` entries of one plugin are two imports with two states. Mounting it into services and naming it in a CLI invocation are the next two slices. **The settings file sits beside the state dir, not inside it — a plugin that can rewrite its own validated settings has settings that were never validated.**
- [ ] Published-port stability per (session, service) so the preview origin survives a fragment port edit (req 18)
- [ ] Compose-fragment merging + security validation of plugin services, preserving fragment-relative path resolution (paths resolve against the fragment's directory in the checkout — set by the fixture) (reqs 3, 5, 16, 20)
- [x] Agent refresh transport: `shipit plugin` shim → worker agent-ops relay → orchestrator, with guard tests (req 12; orchestrator routes are container-denied) — `shipit plugin refresh [name] [--json]`. One verb; `list`/`status` stays reviewed out. The orchestrator route is `POST /api/sessions/:id/plugin/refresh`, `containerAccessible` and therefore in the golden route table; the browser's `/api/plugin-repos` snapshot GET still activates nothing. Local mode's explicit allowlist (`local-agent-ops.ts`) carries the route with the parity test extended, so the dogfood instance cannot silently deny a verb production has. A failed refresh exits non-zero and names the commit still LIVE, because req 15 keeps the prior generation serving — the agent's real problem is that it is working against the old version. Review round (all confirmed at source, all fixed): the refresh did not pass the settled hook, so it swapped the generation and never re-linked `/plugins/<name>` or re-materialized skills — it never reached the agent; it sat ABOVE the docs/178 trust gate that automatic activation sits below, making the agent's verb a way around it; the report was derived from the shared activation-state map, which whichever round finishes last owns, so a concurrent refresh could report a failed install as `unchanged` and exit 0; local mode's relay used `fetch`, so the "unbounded" claim was false there; and the shim ignored `parsed.unsupported`, so a typo silently refreshed everything
- [ ] Egress execution-surface semantics: host satisfaction is agent-container truth today (services are unconfined, docs/172); decide whether plugin services get their own containment (req 24). **Now also covers the install container**, which has general outbound access. What is already settled and enforced: it runs on its own network whose subnet is registered untrusted with `api-container-guard.ts`, so ShipIt's own API — including `/api/sessions/<id>/git/credential` — is 403 from it. The finding that produced this: "not the session's network" was not enough, because the guard reads an unrecognised source IP as a trusted browser/host caller, which made the install container MORE privileged at the API than the agent container it was isolated from
- [ ] Credential name resolution + `secrets_status` plugin grouping (req 23)
- [ ] CLI PATH mechanism + collision checks (reqs 17, 20)
- [x] Skills materialization into each backend's discovery root, namespaced, with refresh re-scan (req 22, docs/209 — one mechanism, one item) — `session/plugin-skills.ts`, materialized on the same prepare pass as the links. Every harness root gets a copy (req 22's "never tied to one backend", and `skillsDirName` also drives ShipIt's own picker); the frontmatter `name:` is rewritten to the namespaced directory name, because the scanner reads the invocable name from the frontmatter and only falls back to the directory; and the copies stay out of the project's git via `.git/info/exclude` (the docs/198 mechanism), since a project's `.gitignore` is a tracked file ShipIt does not own. Only what the consumer `use`s is materialized, and a dropped or renamed import removes what it left behind. Review round (all confirmed at source, all fixed): symlinks in the plugin tree were FOLLOWED by the copy, so a plugin could have pulled `/credentials` into the workspace; the refresh deleted the live directory before copying, so a turn could read a half-written skill and a failed copy wedged that skill permanently; the marker file's presence was treated as proof of ownership, though a handwritten skill could contain one; the name was not injective, so two valid aliases could silently overwrite each other; and `from:` was resolved with the `use` entry's own spelling, which finds nothing on a case-sensitive filesystem when the declaration spells the repo name differently. Second review round (all confirmed at source, all fixed): symlink containment was bypassable through an ANCESTOR of the declared path on either side, so `skills: pkg/skills` with `pkg` a symlink read outside the checkout and a project-owned `.claude -> /outside` was created and populated beyond the exclude; staging directories were neither excluded from git nor swept, so a `git add -A` overlapping a copy could stage a half-copied third-party tree and a killed process left one behind; an orphaned BEGIN marker in `.git/info/exclude` let the next rewrite delete the user's own ignore rules; a per-root partial write left the FILESYSTEM backend-specific even though the result said otherwise (all roots or none now, with rollback); the exclude block was not rewritten when nothing was planned, leaving stale exclusions installed forever; a declared-but-missing skills directory was silent; and the 6-hex name hash had a real, reproducible collision — duplicate names are now rejected outright. **Known gap, deliberately not closed here:** a failed materialization is logged by the orchestrator but has no channel to the Plugins card — container-side prepare state is not part of the activation snapshot. Req 13 wants it visible; that needs a prepare-state channel, which is its own item
- [x] Feedback-channel registration as issue destination (req 25) — declaring a plugin repository is what grants the channel, brokered exactly the way declared trackers are, so no tracker credential enters the session container and req 7 still holds (an issue is filed; nothing is ever pushed). Reported from that session and fixed separately in PR #2225: a generation recorded no source repository, so the feedback footer — and the Plugins tab card with it — could pair a re-pointed declaration with the PREVIOUS repository's commit
- [x] Pin durability (`plugin-pins.ts`): resolved SHA persisted **orchestrator-wide, keyed by the consuming project's declaration** — not per session, or two sessions of one project could resolve a moved tag differently. A recorded pin is honored without re-resolving (a deleted or now-ambiguous tag still activates), a moved tag warns, writes are atomic, and only a declaration edit re-resolves (req 8)
- [x] **Install-before-publish ordering** (reqs 13, 15) — `activateGeneration` takes an injected `runInstall(job)` and calls it against the STAGING checkout, after manifest validation and before the symlink swap. A failed install is now just a failed activation: nothing is published, the staging tree is removed, and the prior generation stays whole and live. Only the consumer's selected exports are offered. The hook is injected because this module runs no plugin-authored code in-process
- [x] **Step 2 — the per-generation overlay volume** (`plugin-overlay.ts`). Reuse `overlay-volume.ts`: `createOverlayVolume(docker, {volumeName, lowerdir, upperdir, workdir}, labels)`, serialized already (overlay2 raises EBUSY on parallel creates). **The constraint that governs this: those three paths must be DAEMON-HOST paths, not orchestrator paths.** The orchestrator sees a generation at `/workspace/sessions/<id>/state/plugins/...`, which in production is inside a Docker volume and means nothing to the daemon — `resolveVolumeMountpoint()` exists precisely to translate, and docs/183 derives its overlay dirs as subpaths of that mountpoint. Get this wrong and volume creation succeeds while the mount is empty or fails at container start, far from the cause. Layout: lowerdir = the pristine generation checkout, upper/work = siblings under the same repo dir, volume name keyed by session + repo + commit (per generation, never per repo) and carrying the `shipit-<session-prefix>_…` orphan-GC convention. **The prefix is 12 characters, verified against the sweep rather than against the convention as described**: `sweepOrphanSessionVolumes` (startup-janitor.ts) matches `^shipit-([a-f0-9-]{12})_` and compares the capture with `sessionId.slice(0, 12)`. The first version of this name used 8 and would never have been reclaimed — the volume would simply have accumulated. A test now asserts the name against that regex. The name also carries a hash of the exact repo name: the readable segment is lossy (`foo.bar` and `foo-bar` both render `foo-bar`), so two valid declarations resolving to commits with a shared 12-character prefix — forks of one history — would have shared a volume, which is the opposite of req 14's independence. And pruning: a superseded generation's `work/<sha>` layer and abandoned `.staging-*` trees are dropped with it — neither was, and neither is named again by anything, so both grew forever
- [x] Plugin `install` execution + stamping (reqs 7, 13, 19) — **in its own throwaway container** (`plugin-install.ts`, user decision 2026-08-13), holding the generation's overlay volume at `/plugin` and **nothing else**: no `/credentials`, no worker URL, no session network, no inherited environment, all capabilities dropped, bounded by a timeout. Runs BEFORE publish, so a failed install degrades to the prior generation instead of replacing it. PR #2202's version — in the agent container, published-then-installed, result discarded — is withdrawn; the environment-scrubbing alternative was offered and declined as best-effort rather than by-construction. Original rationale for not running it orchestrator-side: an earlier draft ran repo-authored install strings in the orchestrator process with its full environment (ShipIt's PAT, unrestricted host access), which is strictly more privileged than `agent.install`. The staging checkout is handed to the worker UID first — overlayfs takes the merged dir's permissions from the LOWER dir, so a root-owned checkout leaves the plugin root unwritable and every install fails at its first file; that handoff also covers generations staged after the container booted. Stamping is in, and is narrower than it first looked: a consumer generation's commit determines every input, so the stamp only exists for the install-succeeded-then-publish-failed re-stage. Second review round (all confirmed at source, all fixed): the network was the credential boundary and `"bridge"` did not provide it; the post-kill reap was unbounded, so a failed kill turned the timeout into a hang; volume release was best-effort, so a still-held volume could publish a generation whose runtime mount cannot be built; cancellation was checked around install but not before or during it; and a lossy volume-name segment let two valid repo names collide
- [x] Settings file: validate declared settings + consumer values, materialize the `SHIPIT_SETTINGS` JSON per imported plugin (req 26) — landed with the state-directory slice above; the resolver is pure, so the Plugins card re-derives resolution issues instead of remembering them, and only a FAILED write is remembered (nothing else can reconstruct "the write did not happen", and a plugin running on the previous declaration's settings must not look healthy)
- [ ] Fetch-authority boundary: repository fetches stay orchestrator-side; guard test that plugin install/services/CLIs cannot reach fetch credentials; standing-grant activation without prompts, identity always visible (req 19). **Install half done** — `plugin-install.test.ts` asserts the container's mount list, its environment and its network directly, so each blocking finding from PR #2202 now fails a build instead of needing a reviewer. Implementation:

- [x] Generation source identity — a generation records the repository it was built from, and `readActiveGeneration` requires the expected source, so a re-pointed declaration can no longer pair a new repository with the previous one's commit; a re-point also retires what the previous repository left, because an `active` symlink that still resolves keeps the container linking `/plugins/<name>` at those files whatever any reader believes. Found by the feedback-channel session's reviewer, confirmed at the source. The req-15 "prior generation keeps serving" test had used a DIFFERENT repository as its stand-in for an unfetchable one, so it was asserting the bug; it now fails the same repository at an unresolvable ref, and the re-point case is its own test
- [x] Generation engine — `plugin-generations.ts`: on-disk layout under the session state dir (docs/246, so a plugin checkout can never be staged into the user's repo), commit resolution (branch tip / pin / durable pin record), staging, phase-2 selector validation, atomic symlink publish (record inside the generation), old-generation pruning that never deletes the live one, a per-repo serial queue, and cancellation checks so a disposed session's activation publishes nothing. Runs no plugin-authored code
- [x] Activation lifecycle — `services/plugin-activation.ts` + wiring through `bootstrap-managers` → `runner-registry-factory` → `service-manager-setup`: runs on session activation and on a `shipit.yaml` edit (container mode) or when a turn ends (local mode, which has no in-container file watcher), fire-and-forget so a slow fetch never delays a session opening (req 13); per-repo independence (req 14); last-attempt state feeds the tab without a GET ever activating anything
- [x] Snapshot + tab states: `active` (with the exact commit), `activating`, `degraded` (prior generation still live — req 15), `unavailable`; tracked-repo selectors resolve against the LIVE generation's manifest (phase 2). The server pushes `plugin_repos_updated` when an activation round settles and the client refetches; the `activating` poll remains as a fallback

- [x] **Merged-view design — resolved 2026-08-13** (consultation, verified against the code): the merged tree cannot exist on the host (the orchestrator has no `CAP_SYS_ADMIN`; docs/183 rejected privileged host overlays), so it lives in a **per-generation `type=overlay` Docker volume** — lowerdir the pristine checkout, upper/work per-generation storage — created by the orchestrator and mounted by the daemon into whichever container attaches it. ONE volume shared by the installer, the services and the CLI-invocation containers (per generation, never per repo: driver options are fixed while consumers hold it). The agent container keeps seeing pristine source only, which is what makes refresh instant. Copying the checkout instead is a correctness fallback where overlay volumes are unavailable, and satisfies req 7 only if the copy is explicitly a disposable runtime materialization with no `.git` — the pristine checkout stays the source of truth
- [x] Container link surface — `session/plugin-runtime.ts` + `POST /plugins/prepare` on the worker, called from `ContainerSessionRunner.preparePlugins()` on the activation-settled hook and again when a container becomes ready (a restarted container loses its links while the generations they address survive). It links each live checkout at `/plugins/<name>` and removes links the declaration no longer names — including when the block is emptied, which is why a round with nothing to activate still settles. **It runs no plugin-authored code and holds no install stamp**; install is not here and must not come back here. `/plugins` itself is created and handed to the worker UID by the entrypoint (without it the non-root worker cannot create the links at all). Requests during a run queue ONE follow-up rather than joining the in-flight promise, since a run reads its state once at the start. **Local mode has no container, so none of this exists there** — exercising it needs a real deployment
- [x] Phase-1 declaration parsing — `src/server/shared/plugin-repos.ts` (called from `shipit-config.ts`; trackers parse first): consumer `repos`+`use` grammar, `exports.plugins` manifest, cross-block name reservation with the same-destination alias exception, alias uniqueness, branch/pin exclusivity, `repo: self` rules; nothing fatal (reqs 11, 13, 27; req 20 phase 1)
- [x] `GET /api/plugin-repos` snapshot — `api-routes-plugin-repos.ts`: per-request config read (issues.trackers precedent), self selectors resolved against the same file's manifest, `consumerRepoUrl`, malformed-document degradation with a warning
- [x] Plugins tab v0 — `plugin-repos-store.ts` (session-scoped; three race guards: foreign-session drop, latest-wins generation, `pending` retry), `PluginReposPanel.tsx`, App.tsx rail wiring: intent gating incl. warnings-only snapshots (req 13), warn dot via `Tab.badge` with accessible label, effective-tab fallback, `useTabLabelCollapse` dep, session reset, `files_changed` shipit.yaml refetch. Tracked repos render an honest "declared — mechanics pending" state that does NOT count toward the dot (the design's never-fetched means "tried and failed"; the full active/degraded/collision states arrive with the slice-2 mechanics). Verified live in the dogfood inner instance against todo-list's merged fixture.
