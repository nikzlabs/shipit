- [x] Per-plugin per-session shared state directory + validated settings file (reqs 17, 18, 26) — `orchestrator/plugin-state.ts` owns the on-disk layout, `shared/plugin-contract.ts` fixes the names both surfaces use (`SHIPIT_PLUGIN_STATE`, `SHIPIT_SETTINGS`, and the container mount points). The state dir deliberately sits OUTSIDE `<sessionDir>/state/`: that subtree is in `REGENERABLE_SESSION_SUBDIRS` and is deleted by disk-tier eviction, while req 18 says this data survives everything short of a session reset. Keyed by `alias`, so two `use:` entries of one plugin are two imports with two states. Mounting it into services and naming it in a CLI invocation are the next two slices. **The settings file sits beside the state dir, not inside it — a plugin that can rewrite its own validated settings has settings that were never validated.**
- [x] Published-port stability per (session, service) so the preview origin survives a fragment port edit (req 18) — **an indirection, not a pinned number.** The origin is `{sessionId}--{port}`, so pinning the number alone would have aimed the subdomain at a dead port the moment a tracked commit moved the fragment's. A plugin service therefore carries TWO numbers: the pinned `publishedPort` the subdomain, the health probe and the browser's service list use, and the `port` the container actually serves on, with `ServiceManager.resolvePreviewTarget` mapping between them. For a PROJECT service the two are always equal — its compose file is the user's, so a change to it is a change the user made
- [x] Compose-fragment merging + security validation of plugin services, preserving fragment-relative path resolution (reqs 3, 5, 16, 20) — **the fragment is never handed to `docker compose -f`.** Compose resolves relative paths against the BASE file's project directory, so a plugin's `- .:/app` would mount the consuming project; and neither `include` semantics nor a path rebase is sufficient, because what a fragment's `.` must resolve to is not a daemon-filesystem path at all but a SUBPATH OF A DOCKER VOLUME — the generation's overlay. ShipIt therefore parses, validates and re-emits every service into the generated override with each relative source rewritten onto the plugin's own tree. Re-emitting is what makes the validation a boundary rather than a lint: ShipIt authors every line the daemon sees. The service keys are an ALLOWLIST — everything a service says about itself, nothing about its relationship to the host — because a denylist silently passes the next key Compose adds, and a fragment is third-party code that re-executes on every tracked-branch commit under req 19's standing grant. A project that declares plugins and no `compose:` block still gets their services (req 5: one declaration, no boilerplate)
- [x] Agent refresh transport: `shipit plugin` shim → worker agent-ops relay → orchestrator, with guard tests (req 12; orchestrator routes are container-denied) — `shipit plugin refresh [name] [--json]`. One verb; `list`/`status` stays reviewed out. The orchestrator route is `POST /api/sessions/:id/plugin/refresh`, `containerAccessible` and therefore in the golden route table; the browser's `/api/plugin-repos` snapshot GET still activates nothing. Local mode's explicit allowlist (`local-agent-ops.ts`) carries the route with the parity test extended, so the dogfood instance cannot silently deny a verb production has. A failed refresh exits non-zero and names the commit still LIVE, because req 15 keeps the prior generation serving — the agent's real problem is that it is working against the old version. - [x] Container-side prepare failures reach the Plugins card (req 13, req 22) — prepare has two halves that fail independently: the orchestrator writes each import's state directory and settings file, and the container links `/plugins/<name>` and materializes skills. The second half ended at a log line. The two are kept in SEPARATE maps and concatenated on read, because each actor may only replace its own entries — a container prepare that reports nothing must not erase a settings-write failure recorded microseconds earlier. The worker's response is VALIDATED, not cast: a container outlives an orchestrator restart, so a rolling upgrade can leave a new orchestrator talking to a worker built before failures carried a repository name, and casting filed those under `sessionId::undefined` — invisible, and displacing the previous run's record
- [x] Egress **execution** surface for plugin services (req 24, the containment half only) — **already satisfied; no plugin-specific work.** The question was raised from a stale plan note about the docs/172 residual ("compose services are unconfined"); docs/263 has since shipped compose service egress containment, and plugin services take the same `containEgress` path as project services (`services/plugin-services.ts`, `services/plugin-preflight.ts` → `readProjectServices` / `collectPluginFragments`). A plugin service is therefore contained exactly as an equivalent same-repo service is, which is what req 24 asks for. **Second scope correction (2026-08-15, found by #2265): that covers SERVICES only.** The companion-CLI invocation container joins `PLUGIN_CLI_NETWORK` through `ensureUntrustedPluginNetwork` (`plugin-container.ts:61`), which creates a plain NAT bridge — it registers that subnet as untrusted at ShipIt's own API, which is the req 19 boundary, and installs **no firewall, no resolver and no SNI proxy**, which is the req 24 one. So a companion CLI (and the install container) has **unrestricted outbound egress today**, while req 24 says services and companion CLIs "reach exactly what equivalent same-repo code could reach". The 2026-08-14 resolved question verified the SERVICE path correctly and its scope was never widened; see the item below Also settled and enforced: the install container runs on its own network whose subnet is registered untrusted with `api-container-guard.ts`, so ShipIt's own API is 403 from it, and that network is pinned non-dual-stack because the guard matches IPv4 CIDRs only — an unrecognised source IP reads as a trusted browser/host caller, which would have made the install container MORE privileged at the API than the agent container it was isolated from. **Scope correction (2026-08-14): this item was ticked as "req 24 satisfied", and it is not — it satisfies the CONTAINMENT half only.** Req 24 has a second half in its own words: a project session "shows which declared hosts are not yet allowed (the same visibility req 23 gives credentials), and ShipIt offers an affordance to add the declared hosts to the user's egress allowlist — for the session or for the whole ShipIt instance — as a deliberate user act." That half is unbuilt; see the item below
- [x] **Req 24's enforcement half now covers the companion-CLI and install containers** (gap found by #2265, closed in #2268) — `containComposeServices` gives a plugin SERVICE the same egress containment a same-repo service gets, and nothing equivalent runs for the invocation or install containers: `ensureUntrustedPluginNetwork` makes their network deniable at ShipIt's API and does nothing about the internet. **The two boundaries are different and it is easy to read one as the other** — untrusted-network registration is req 19 (a plugin must not reach a fetch credential, which it now cannot), while req 24 is about what a plugin can call OUT to. A guard test asserting the first passes while the second is open, which is the same shape as the service-surface finding in planning#371. **The shape decision was between joining the session's own contained egress and getting an equivalent of its own, and req 19 — not taste — ruled the first out**: sharing the agent container's namespace makes the worker's loopback the plugin's own, and `/agent-ops/*` is loopback-only and needs no token, so `git -C /project fetch` becomes a GitHub-token read with no mount and no variable changed; while joining the session bridge gives the container an address in no registered untrusted subnet, which `api-container-guard.ts` reads as a BROWSER/HOST caller — more API reach than the agent container it was isolated from. So each container gets its own namespace on the same untrusted plugin network, carrying the docs/172 Tier A/B/C stack built from `ContainerSessionManager.resolveEgress` — **the same seam `plugin-hosts.ts` reports the card from, so enforcement and the card cannot disagree**, asserted as an executable claim that derives both answers from one session state and compares them host by host. **A holder, not a pause.** Containment must be in place before the plugin's first instruction. Compose services close that window by starting on an `internal` network and installing while paused, because Compose starts those containers and ShipIt does not; ShipIt creates these two, so a trusted holder container (no repo code, no mounts, nothing listening) is started and contained first and the workload joins it with `NetworkMode: container:<holder>`. No uncontained instant, and no pause to be interrupted in. **Two deliberate narrowings**: the resolver gets no `internalDomains`, so a plugin container cannot resolve the orchestrator (it has no callback to make); and the SNI proxy gets no Tier C `decisionUrl`, because that request would be 403 under req 19 — instead the session's in-memory allow-once hosts are snapshotted into the static allowlist at launch, which is what makes the container's reach EXACTLY `pluginHostAllowance`'s report rather than a subset of it. **One defect found while building it, and it is the kind only building finds**: the holder was first labelled `shipit-parent-session` by analogy with every other session-scoped container — and that label is what `compose-cli.ts`'s `killStaleContainers` `docker rm -f`s before EVERY Compose start, sparing only a resolver/proxy whose netns parent is live. A holder carries neither keep-label, so any `shipit service start` in the session would have deleted the namespace a running companion CLI was executing in, and taken its resolver and proxy with it. The holders now carry only their own plugin label, with the whole label set pinned in a test and the reasoning attached
- [x] **Req 24's visibility half: declared hosts on the card, with the grant** (gap found by #2263, shipped in #2265) — `hosts` is parsed into `PluginExport` (`shared/plugin-repos.ts`) and then goes nowhere: no field on `PluginRepoUseView`, no row in `PluginReposPanel`, no "Allow (session)" / "Allow (instance)" affordance. `plan.md` §3's "Needs — hosts" row carries no ✓, so the design never claimed it either — this is an unbuilt surface, not a defect, and it had no checklist item because the containment item above was mistakenly read as covering the whole requirement. The shape to follow is req 23's, which this requirement's own text points at: names resolved from the LIVE generation's manifest, rendered as satisfied/missing on the card. The part that is NOT req 23's shape is the affordance — adding a host to an egress allowlist is a deliberate user act with two scopes (session, instance), so it needs docs/263's allowlist surface rather than a plugin-local one — and that is what shipped: the grant posts to the EXISTING `POST /api/egress/hosts` at `scope: <sessionId>` and `scope: global`, and `shared/plugin-hosts.ts` takes an `isAllowed` predicate and returns a projection, so the manifest is an input to the REPORT and never to the ANSWER (an integration test asserts that reading the card leaves the allowlist untouched). **The visibility half reuses req 23's machinery rather than paralleling it** — one collector walk in `shared/plugin-needs.ts`, which both need surfaces call, so the four rules live once: a repo with no `use:` declares nothing; a repository whose live manifest cannot be READ reports nothing, never "needs nothing" (req 13); a selector naming no exported plugin is skipped; names de-duplicated in manifest order. Two copies of that middle rule is how one surface starts calling an unread manifest satisfied. **"Not yet allowed" is answered from the seam that CONFIGURES enforcement, not re-derived from the allowlist store**, and the review round is why: the first revision derived it from the store, and a docs/211 Network-off sandbox runs on the lifeline base with an EMPTY extras list, so a store-derived answer reported npm, MCP hosts and every user-added entry as reachable in a session that can reach none of them. It now asks two questions of two sources — is this session contained at all (`isEgressContained`, so an Open session shows no rows and nobody is sent to grant what was never blocked), and what may a contained session reach (the session's own `ResolvedEgressConfig`, newly exposed as `ContainerSessionManager.resolveEgress`, plus allow-once). **Two stated limits**: an instance-scoped grant reloads the resolver/proxy only for a session-scoped add, though the proxy's decision endpoint honours a global entry live for a host outside the static set, so the button's title says when it takes effect; and the rows say a host is "not in this session's egress allowlist" rather than that a call was blocked. The satisfied side is stated quietly too, because req 24 asks the session to show what a plugin NEEDS and not only what is broken
- [x] **Credential DELIVERY to plugin services (req 23, shipped in #2264)** — found by the self-use slice's reviewer, confirmed at the source and NOT self-specific: `buildPluginComposeServices` merges the fragment's own environment with `pluginEnvironment` (the `SHIPIT_*` names only), a fragment may not name a value it does not carry (`x-shipit-secrets` refused, pass-through `- FOO` refused), and `service-secrets-resolver.ts` reads a plugin's declared names for the SATISFIED/MISSING status alone. So the card can say `PROBE_TOKEN` is satisfied while the service that declared it receives nothing — the delivery half the CLI surface already has (`declaredCredentialEnv`). The name-resolution item below is genuinely done; this is the other half of req 23, and it belongs to whoever owns the service surface. **Delivered as the service's own `environment` in the generated override, not as an `env_file`** — the first implementation used a file, on the reasoning that it matched the project's own secrets path, and an independent review showed that path cannot hold the requirement: Compose gives `environment` precedence over `env_file`, so a plugin declaring a name in its manifest AND setting it in its own fragment would run on the fragment's literal while the card reported the project's stored value satisfied — the exact disagreement being fixed; and Compose's env-file parser applies quote, comment and `${VAR}` handling, so a stored value is not necessarily delivered byte-for-byte and `${…}` could resolve from the environment of the process that runs Compose, which is the ORCHESTRATOR's. Emitting into `environment` puts every value through the same `escapeDollars` the rest of a plugin definition already gets, and removed a whole mechanism — no new file, no second sweep domain, no delivery-mode branch. **The CLI's `declaredCredentialEnv` was deliberately NOT reused and not copied**: it is shaped for the Docker API, takes `PluginCliDeps`, and reads the store twice, while the compose surface already holds the exact map the card's verdict is computed from, in the same function — so its delivery is one filter over one map. What IS shared is the RULE: `satisfiedCredentialNames` (`shared/plugin-credentials.ts`) is now the single definition both store readers delegate to, so the CLI, the card and the service path cannot drift on what "satisfied" means. **A declared-but-unset credential is omitted and the service still starts** — the manifest declares names with no required/optional distinction, so refusing to start would make every optional key fatal and, under the all-or-nothing service rule, take out a whole repository over one unset name; the companion CLI already omits-and-runs, and two surfaces disagreeing about one declared name is the worse failure. The gap stays named on the card (req 13). **Honest cost, stated rather than hidden**: the generated override is now the one ShipIt-written file that carries secret values. It lives in the session state dir — never the git clone, and outside the `plugins/` subtree that is the agent container's only mount of it — and `writeComposeOverride` now writes it `0600` on every write. **Three limits stated rather than closed**: a running MANUAL plugin service keeps the values it started with, since `refreshSecrets()` re-ups only `auto` services and changing that would restart a user's manually started service on every secret save; a failed reconcile after a refresh leaves the card describing a generation the stack is not running, which is `refreshPluginServices`'s existing failure mode over the whole generation rather than anything credential-specific; and a plugin may declare a credential named after a ShipIt contract variable — see the item below

- [x] Skills materialization into each backend's discovery root, namespaced, with refresh re-scan (req 22, docs/209 — one mechanism, one item) — `session/plugin-skills.ts`, materialized on the same prepare pass as the links. Every harness root gets a copy (req 22's "never tied to one backend", and `skillsDirName` also drives ShipIt's own picker); the frontmatter `name:` is rewritten to the namespaced directory name, because the scanner reads the invocable name from the frontmatter and only falls back to the directory; and the copies stay out of the project's git via `.git/info/exclude` (the docs/198 mechanism), since a project's `.gitignore` is a tracked file ShipIt does not own. Only what the consumer `use`s is materialized, and a dropped or renamed import removes what it left behind. - [x] **Step 2 — the per-generation overlay volume** (`plugin-overlay.ts`). Reuse `overlay-volume.ts`: `createOverlayVolume(docker, {volumeName, lowerdir, upperdir, workdir}, labels)`, serialized already (overlay2 raises EBUSY on parallel creates). **The constraint that governs this: those three paths must be DAEMON-HOST paths, not orchestrator paths.** The orchestrator sees a generation at `/workspace/sessions/<id>/state/plugins/...`, which in production is inside a Docker volume and means nothing to the daemon — `resolveVolumeMountpoint()` exists precisely to translate, and docs/183 derives its overlay dirs as subpaths of that mountpoint. Get this wrong and volume creation succeeds while the mount is empty or fails at container start, far from the cause. Layout: lowerdir = the pristine generation checkout, upper/work = siblings under the same repo dir, volume name keyed by session + repo + commit (per generation, never per repo) and carrying the `shipit-<session-prefix>_…` orphan-GC convention. **The prefix is 12 characters, verified against the sweep rather than against the convention as described**: `sweepOrphanSessionVolumes` (startup-janitor.ts) matches `^shipit-([a-f0-9-]{12})_` and compares the capture with `sessionId.slice(0, 12)`. The name also carries a hash of the exact repo name: the readable segment is lossy (`foo.bar` and `foo-bar` both render `foo-bar`), so two valid declarations resolving to commits with a shared 12-character prefix — forks of one history — would have shared a volume, which is the opposite of req 14's independence. - [x] Plugin `install` execution + stamping (reqs 7, 13, 19) — **in its own throwaway container** (`plugin-install.ts`, user decision 2026-08-13), holding the generation's overlay volume at `/plugin` and **nothing else**: no `/credentials`, no worker URL, no session network, no inherited environment, all capabilities dropped, bounded by a timeout.
