Next design slice (server mechanics):

- [x] Checkout mechanics: bare-cache reuse (serialized per cache), per-generation checkout in the session state dir (req 2). **Correction (2026-08-13):** an earlier version of this item said the generation directory IS the writable layer and the CoW layer "buys nothing". Req 7 says install output lives somewhere that is neither plugin source nor project data, so the checkout stays pristine and the CoW layer is back — it buys exactly that requirement
- [x] Mounts (agent container half): the session's plugin root mounted **read-only** at `/plugin-store`, with `/plugins/<name>` a container-side symlink through it, so a generation swap is visible without recreating the container (reqs 2, 7). The store-not-generation shape is settled and reviewer-confirmed (Docker resolves a bind source's symlinks at creation, so a per-generation mount would pin one generation); the writable twin in PR #2202 is **withdrawn** — the agent container gets no writable view at any path. `/project` for services lands with the compose work (req 21)
- [x] Generation staging/activation: stage → validate (incl. phase-2 selectors) → atomic symlink swap; the record lives inside the generation so reads are atomic; failure keeps the prior generation whole and live; a per-repo serial QUEUE (not promise-joining, so a mid-flight declaration edit is never lost); prune never deletes the live generation (reqs 12, 13, 14, 15). Service prepare/recreate lands with the compose work
- [x] Per-plugin per-session shared state directory + validated settings file (reqs 17, 18, 26) — `orchestrator/plugin-state.ts` owns the on-disk layout, `shared/plugin-contract.ts` fixes the names both surfaces use (`SHIPIT_PLUGIN_STATE`, `SHIPIT_SETTINGS`, and the container mount points). The state dir deliberately sits OUTSIDE `<sessionDir>/state/`: that subtree is in `REGENERABLE_SESSION_SUBDIRS` and is deleted by disk-tier eviction, while req 18 says this data survives everything short of a session reset. Keyed by `alias`, so two `use:` entries of one plugin are two imports with two states. Mounting it into services and naming it in a CLI invocation are the next two slices. **The settings file sits beside the state dir, not inside it — a plugin that can rewrite its own validated settings has settings that were never validated.**
- [x] Published-port stability per (session, service) so the preview origin survives a fragment port edit (req 18) — **an indirection, not a pinned number.** The origin is `{sessionId}--{port}`, so pinning the number alone would have aimed the subdomain at a dead port the moment a tracked commit moved the fragment's. A plugin service therefore carries TWO numbers: the pinned `publishedPort` the subdomain, the health probe and the browser's service list use, and the `port` the container actually serves on, with `ServiceManager.resolvePreviewTarget` mapping between them. For a PROJECT service the two are always equal — its compose file is the user's, so a change to it is a change the user made
- [x] Compose-fragment merging + security validation of plugin services, preserving fragment-relative path resolution (reqs 3, 5, 16, 20) — **the fragment is never handed to `docker compose -f`.** Compose resolves relative paths against the BASE file's project directory, so a plugin's `- .:/app` would mount the consuming project; and neither `include` semantics nor a path rebase is sufficient, because what a fragment's `.` must resolve to is not a daemon-filesystem path at all but a SUBPATH OF A DOCKER VOLUME — the generation's overlay. ShipIt therefore parses, validates and re-emits every service into the generated override with each relative source rewritten onto the plugin's own tree. Re-emitting is what makes the validation a boundary rather than a lint: ShipIt authors every line the daemon sees. The service keys are an ALLOWLIST — everything a service says about itself, nothing about its relationship to the host — because a denylist silently passes the next key Compose adds, and a fragment is third-party code that re-executes on every tracked-branch commit under req 19's standing grant. A project that declares plugins and no `compose:` block still gets their services (req 5: one declaration, no boilerplate)
- [x] Agent refresh transport: `shipit plugin` shim → worker agent-ops relay → orchestrator, with guard tests (req 12; orchestrator routes are container-denied) — `shipit plugin refresh [name] [--json]`. One verb; `list`/`status` stays reviewed out. The orchestrator route is `POST /api/sessions/:id/plugin/refresh`, `containerAccessible` and therefore in the golden route table; the browser's `/api/plugin-repos` snapshot GET still activates nothing. Local mode's explicit allowlist (`local-agent-ops.ts`) carries the route with the parity test extended, so the dogfood instance cannot silently deny a verb production has. A failed refresh exits non-zero and names the commit still LIVE, because req 15 keeps the prior generation serving — the agent's real problem is that it is working against the old version. Review round (all confirmed at source, all fixed): the refresh did not pass the settled hook, so it swapped the generation and never re-linked `/plugins/<name>` or re-materialized skills — it never reached the agent; it sat ABOVE the docs/178 trust gate that automatic activation sits below, making the agent's verb a way around it; the report was derived from the shared activation-state map, which whichever round finishes last owns, so a concurrent refresh could report a failed install as `unchanged` and exit 0; local mode's relay used `fetch`, so the "unbounded" claim was false there; and the shim ignored `parsed.unsupported`, so a typo silently refreshed everything
- [x] Container-side prepare failures reach the Plugins card (req 13, req 22) — prepare has two halves that fail independently: the orchestrator writes each import's state directory and settings file, and the container links `/plugins/<name>` and materializes skills. The second half ended at a log line. The two are kept in SEPARATE maps and concatenated on read, because each actor may only replace its own entries — a container prepare that reports nothing must not erase a settings-write failure recorded microseconds earlier. The worker's response is VALIDATED, not cast: a container outlives an orchestrator restart, so a rolling upgrade can leave a new orchestrator talking to a worker built before failures carried a repository name, and casting filed those under `sessionId::undefined` — invisible, and displacing the previous run's record
- [x] Egress execution surface for plugin services (req 24) — **already satisfied; no plugin-specific work.** The question was raised from a stale plan note about the docs/172 residual ("compose services are unconfined"); docs/263 has since shipped compose service egress containment, and plugin services take the same `containEgress` path as project services (`services/plugin-services.ts`, `services/plugin-preflight.ts` → `readProjectServices` / `collectPluginFragments`). A plugin service is therefore contained exactly as an equivalent same-repo service is, which is what req 24 asks for. Also settled and enforced: the install container runs on its own network whose subnet is registered untrusted with `api-container-guard.ts`, so ShipIt's own API is 403 from it, and that network is pinned non-dual-stack because the guard matches IPv4 CIDRs only — an unrecognised source IP reads as a trusted browser/host caller, which would have made the install container MORE privileged at the API than the agent container it was isolated from
- [ ] **Credential DELIVERY to plugin services (req 23)** — found by the self-use slice's reviewer, confirmed at the source and NOT self-specific: `buildPluginComposeServices` merges the fragment's own environment with `pluginEnvironment` (the `SHIPIT_*` names only), a fragment may not name a value it does not carry (`x-shipit-secrets` refused, pass-through `- FOO` refused), and `service-secrets-resolver.ts` reads a plugin's declared names for the SATISFIED/MISSING status alone. So the card can say `PROBE_TOKEN` is satisfied while the service that declared it receives nothing — the delivery half the CLI surface already has (`declaredCredentialEnv`). The name-resolution item below is genuinely done; this is the other half of req 23, and it belongs to whoever owns the service surface
- [x] Credential name resolution + `secrets_status` plugin grouping (req 23) — a plugin's declared credential names are read from the LIVE generation's own manifest and resolved against the CONSUMING project's secret store, keyed by that project's remote. The store boundary is held by construction rather than by a comment: the resolver takes `SecretStore` (user-typed values) and cannot reach `CredentialStore` (ShipIt's GitHub identity, tracker and agent tokens) because the parameter type admits nothing else, and it returns NAMES only, so nothing downstream is in a position to leak a value. A test proves it with both stores populated. Follow-up in PR #2225: `readActiveManifest` read that manifest by declaration name alone, so a re-pointed declaration would have reported the PREVIOUS repository's credential names as this project's gap — it now takes the expected source like every other reader through the `active` symlink
- [x] CLI PATH mechanism + collision checks (reqs 17, 20) — companion CLIs on the agent's PATH (#2229), the wrapper pass resolving a plugin's live generation once (#2237), and the collision verdict recomputed per snapshot rather than remembered. The invocation path pins `active` ONCE and reads the record, manifest, entrypoint, overlay lowerdir and volume name out of that single answer, so a refresh landing mid-call can no longer produce a volume named for one generation over another's tree
- [x] Skills materialization into each backend's discovery root, namespaced, with refresh re-scan (req 22, docs/209 — one mechanism, one item) — `session/plugin-skills.ts`, materialized on the same prepare pass as the links. Every harness root gets a copy (req 22's "never tied to one backend", and `skillsDirName` also drives ShipIt's own picker); the frontmatter `name:` is rewritten to the namespaced directory name, because the scanner reads the invocable name from the frontmatter and only falls back to the directory; and the copies stay out of the project's git via `.git/info/exclude` (the docs/198 mechanism), since a project's `.gitignore` is a tracked file ShipIt does not own. Only what the consumer `use`s is materialized, and a dropped or renamed import removes what it left behind. Review round (all confirmed at source, all fixed): symlinks in the plugin tree were FOLLOWED by the copy, so a plugin could have pulled `/credentials` into the workspace; the refresh deleted the live directory before copying, so a turn could read a half-written skill and a failed copy wedged that skill permanently; the marker file's presence was treated as proof of ownership, though a handwritten skill could contain one; the name was not injective, so two valid aliases could silently overwrite each other; and `from:` was resolved with the `use` entry's own spelling, which finds nothing on a case-sensitive filesystem when the declaration spells the repo name differently. Second review round (all confirmed at source, all fixed): symlink containment was bypassable through an ANCESTOR of the declared path on either side, so `skills: pkg/skills` with `pkg` a symlink read outside the checkout and a project-owned `.claude -> /outside` was created and populated beyond the exclude; staging directories were neither excluded from git nor swept, so a `git add -A` overlapping a copy could stage a half-copied third-party tree and a killed process left one behind; an orphaned BEGIN marker in `.git/info/exclude` let the next rewrite delete the user's own ignore rules; a per-root partial write left the FILESYSTEM backend-specific even though the result said otherwise (all roots or none now, with rollback); the exclude block was not rewritten when nothing was planned, leaving stale exclusions installed forever; a declared-but-missing skills directory was silent; and the 6-hex name hash had a real, reproducible collision — duplicate names are now rejected outright. **The gap this item recorded is now closed** (see the container-prepare item below): a failed materialization used to end at a `console.warn`, so a plugin that shipped none of the agent instructions it promised still rendered as a healthy card
- [x] Feedback-channel registration as issue destination (req 25) — declaring a plugin repository is what grants the channel, brokered exactly the way declared trackers are, so no tracker credential enters the session container and req 7 still holds (an issue is filed; nothing is ever pushed). Reported from that session and fixed separately in PR #2225: a generation recorded no source repository, so the feedback footer — and the Plugins tab card with it — could pair a re-pointed declaration with the PREVIOUS repository's commit
- [x] Pin durability (`plugin-pins.ts`): resolved SHA persisted **orchestrator-wide, keyed by the consuming project's declaration** — not per session, or two sessions of one project could resolve a moved tag differently. A recorded pin is honored without re-resolving (a deleted or now-ambiguous tag still activates), a moved tag warns, writes are atomic, and only a declaration edit re-resolves (req 8)
- [x] **Install-before-publish ordering** (reqs 13, 15) — `activateGeneration` takes an injected `runInstall(job)` and calls it against the STAGING checkout, after manifest validation and before the symlink swap. A failed install is now just a failed activation: nothing is published, the staging tree is removed, and the prior generation stays whole and live. Only the consumer's selected exports are offered. The hook is injected because this module runs no plugin-authored code in-process
- [x] **Step 2 — the per-generation overlay volume** (`plugin-overlay.ts`). Reuse `overlay-volume.ts`: `createOverlayVolume(docker, {volumeName, lowerdir, upperdir, workdir}, labels)`, serialized already (overlay2 raises EBUSY on parallel creates). **The constraint that governs this: those three paths must be DAEMON-HOST paths, not orchestrator paths.** The orchestrator sees a generation at `/workspace/sessions/<id>/state/plugins/...`, which in production is inside a Docker volume and means nothing to the daemon — `resolveVolumeMountpoint()` exists precisely to translate, and docs/183 derives its overlay dirs as subpaths of that mountpoint. Get this wrong and volume creation succeeds while the mount is empty or fails at container start, far from the cause. Layout: lowerdir = the pristine generation checkout, upper/work = siblings under the same repo dir, volume name keyed by session + repo + commit (per generation, never per repo) and carrying the `shipit-<session-prefix>_…` orphan-GC convention. **The prefix is 12 characters, verified against the sweep rather than against the convention as described**: `sweepOrphanSessionVolumes` (startup-janitor.ts) matches `^shipit-([a-f0-9-]{12})_` and compares the capture with `sessionId.slice(0, 12)`. The first version of this name used 8 and would never have been reclaimed — the volume would simply have accumulated. A test now asserts the name against that regex. The name also carries a hash of the exact repo name: the readable segment is lossy (`foo.bar` and `foo-bar` both render `foo-bar`), so two valid declarations resolving to commits with a shared 12-character prefix — forks of one history — would have shared a volume, which is the opposite of req 14's independence. And pruning: a superseded generation's `work/<sha>` layer and abandoned `.staging-*` trees are dropped with it — neither was, and neither is named again by anything, so both grew forever
- [x] Plugin `install` execution + stamping (reqs 7, 13, 19) — **in its own throwaway container** (`plugin-install.ts`, user decision 2026-08-13), holding the generation's overlay volume at `/plugin` and **nothing else**: no `/credentials`, no worker URL, no session network, no inherited environment, all capabilities dropped, bounded by a timeout. Runs BEFORE publish, so a failed install degrades to the prior generation instead of replacing it. PR #2202's version — in the agent container, published-then-installed, result discarded — is withdrawn; the environment-scrubbing alternative was offered and declined as best-effort rather than by-construction. Original rationale for not running it orchestrator-side: an earlier draft ran repo-authored install strings in the orchestrator process with its full environment (ShipIt's PAT, unrestricted host access), which is strictly more privileged than `agent.install`. The staging checkout is handed to the worker UID first — overlayfs takes the merged dir's permissions from the LOWER dir, so a root-owned checkout leaves the plugin root unwritable and every install fails at its first file; that handoff also covers generations staged after the container booted. Stamping is in, and is narrower than it first looked: a consumer generation's commit determines every input, so the stamp only exists for the install-succeeded-then-publish-failed re-stage. Second review round (all confirmed at source, all fixed): the network was the credential boundary and `"bridge"` did not provide it; the post-kill reap was unbounded, so a failed kill turned the timeout into a hang; volume release was best-effort, so a still-held volume could publish a generation whose runtime mount cannot be built; cancellation was checked around install but not before or during it; and a lossy volume-name segment let two valid repo names collide
- [x] Settings file: validate declared settings + consumer values, materialize the `SHIPIT_SETTINGS` JSON per imported plugin (req 26) — landed with the state-directory slice above; the resolver is pure, so the Plugins card re-derives resolution issues instead of remembering them, and only a FAILED write is remembered (nothing else can reconstruct "the write did not happen", and a plugin running on the previous declaration's settings must not look healthy)
- [ ] Fetch-authority boundary: repository fetches stay orchestrator-side; guard test that plugin install/services/CLIs cannot reach fetch credentials; standing-grant activation without prompts, identity always visible (req 19). **Install and CLI halves done** — `plugin-install.test.ts` and `plugin-cli-run.test.ts` assert each container's mounts, environment and network directly, so each blocking finding from PR #2202 fails a build instead of needing a reviewer. The CLI half states its mount and environment claims EXHAUSTIVELY (the whole list, compared) rather than as a denylist of today's known-bad names, because this is the half a later change breaks by addition; the install half is still denylist-shaped (one `Binds` entry, an env regex) and has no `Mounts`/`VolumesFrom`/`NetworkingConfig` assertion at all — worth converting when that file is next touched. Three things the CLI half needed that install did not: (a) the container must not share the session worker's **network namespace** — it runs the worker IMAGE, so `shipit-git-credential` is present in it and `/project`'s git config names that helper, and the helper needs no token and no URL (it POSTs unauthenticated to `127.0.0.1:9100/agent-ops/git/credential`), so `NetworkMode: host` or `container:<session>` alone would turn `git -C /project fetch` into a token read with no mount and no env var changed; (b) `WORKER_PORT` is as dangerous as an explicit worker URL, for the same fallback; (c) the boundary is re-asserted on the settings and `repo: self` branches, not once on the main path, because a branch is where it erodes. **Two limits are stated rather than closed.** The exhaustive env claim covers what ShipIt SUBMITS, not the container's effective environment — Docker merges the image's own `ENV` (the worker image already supplies `PATH`, `AGENT_HOME`), so an `ENV GITHUB_TOKEN=…` added to `Dockerfile.session-worker.*` would reach plugin code with every assertion green; that is the image's contract and nothing here guards it. And see the `/project/.git` item below. **Services outstanding for want of a surface, not for want of a test** — the plugin-service path does not exist yet (the "Compose-fragment merging…" item above is open; there is no plugin-fragment merge and no plugin-service container creation anywhere), and its containment shape is itself an open decision under the egress item, so a guard test written now would be inventing the design it is supposed to guard
- [ ] **A credential is never persisted to reach a repository** (req 19, amended 2026-08-14) — ShipIt's own machinery already meets this: `repo-git.ts` resets inherited helpers and installs a per-origin `credential.<origin>.helper`, so a token is supplied for the life of a fetch and written nowhere. The gap is a credential a USER typed into a repository URL: `addRepo` (`services/repos.ts`) never calls `stripUrlCredentials`, `RepoStore.add` persists the string verbatim, and `RepoGit.cloneFromCache` runs `git remote set-url origin <that string>` — so it lands in `/project/.git/config`, which every plugin CLI can read and every plugin service will be able to. No mount, environment or network assertion on the plugin surfaces can detect it, which is why the req-19 guard tests pass while the boundary is open. **The user's decision (receipt in `requirements.md`): do for plugins what the regular session path already does — do not save the credential.** Strip it on add and rely on the helper. `stripUrlCredentials` exists and is currently used only on the `shipit-source.ts` self-update path. Known cost, accepted: a remote whose ONLY working auth is an embedded URL credential stops working on the helper path
- [x] **Every subnet a plugin network reports must be deniable, not merely one of them** (req 19) — found while writing the CLI guard tests, fixed in `plugin-container.ts`. `api-container-guard.ts` matches IPv4 CIDRs only, so a **dual-stack** network passed the old check (one registerable IPv4 subnet) while every container on it also held an IPv6 address in no registered CIDR — which the guard reads as a trusted browser/host caller, i.e. the exact escalation the dedicated network exists to prevent, reachable by making the same request over IPv6. The old code's fail-closed branch fired only when NO subnet was registerable. Now every reported subnet must register, and the network ShipIt creates is pinned `EnableIPv6: false` so a daemon default cannot make it dual-stack; the remaining check covers a network ShipIt did not create (a leftover from an earlier boot). Applies to install and CLI at once, which is why the control is shared code
- [x] Live-manifest readers: the two ORCHESTRATOR copies are collapsed (PR #2232, merged) (`plugin-state.ts` now calls the engine's `readActiveManifest` instead of its own duplicate). What remains is `session/plugin-skills.ts` → `readExports`, and it **stays by design** — `eslint.config.js` makes `session/` ↔ `orchestrator/` imports a hard error in both directions, type imports included, because they are different processes, and for plugins it is also the "orchestrator says *when*, never *what*" split: the container reads each plugin's own manifest out of its live checkout so the orchestrator never ships the export list. A future three-way fold would have to extract the parse body into a NEW `src/server/shared/` module — not `shared/plugin-repos.ts`, which is deliberately filesystem-free so the client can import it — and is not worth doing for one identical 12-line body. The one folded call site needed the expected-source argument added on top, which PR #2225 does
- [x] **The CONTAINER side checks the generation's source too — three readers, one owner** (independent review of PR #2225; shipped in #2236). #2225 guarded every orchestrator reader and the CLI invocation path, while `src/server/session/` had no record check at all — so a generation the orchestrator refused was still the one the AGENT got: `/plugins/<name>` mounted, its `SKILL.md` files materialized into the agent's skill roots, its command names on PATH. Skills are the sharp edge — a checkout is files the agent MAY read; a materialized skill is instructions it FOLLOWS, from a repository the declaration no longer names. The window is not symlink-swap-sized either: `retireForeignGeneration` runs inside an activation round, and that round is fire-and-forget behind a git fetch and possibly a container install, so a re-point whose new fetch fails never closes it. Resolved with `shared/plugin-generation-record.ts` — the record format as an on-disk contract with a FAIL-CLOSED reader (a non-object, or a non-string `source`, reads as having no source, so a corrupt file cannot decide a foreign checkout is this declaration's) — plus ONE memoized verified resolution per declared repo shared by the links, the skills and the commands, and `removeDeadLink()` to withdraw a link already made. `plugin-cli.ts` now reads the store nowhere and takes a required `checkoutFor(repo)`, which closed the last unpinned half of the pass. **This is what makes #2225's decision to KEEP a source-less generation safe**: nothing can prove whose it is, so it is not deleted — and not exposed either. Cost, stated rather than hidden: after deploy an existing session's plugins read as unavailable until the next successful activation republishes them with a source
- [x] **One consumer lease over a live generation, covering plugin services AND CLI invocations** (`plugin-leases.ts`) — publication pruned the previous checkout and its writable layer with no lease, so a refresh could delete a generation out from under a container that still had it mounted. Found by the CLI session's review. Req 15 is the requirement it serves. **One lease, two facts, because they cover different lifetimes**: an in-process hold, taken in the same SYNCHRONOUS block that resolves `active` and released in a `finally`, covering the window from resolving a generation to the moment a container holds it — a window that is not benign, because Docker re-creates a missing named volume at container start as an empty one, so the failure there is a silently empty `/plugin`; and the volume's own attachment, which the daemon enforces and `removePluginOverlay` already verifies, which is the half that survives an orchestrator restart and the half that covers a plugin *service* (a container the call that created it does not outlive). Symmetrically, the pruner CLAIMS synchronously before it awaits anything, so a hold cannot slip between its check and its `rm`. **Never released is bounded, not broken**: a stale hold costs one undeleted generation directory inside a session state dir that dies with the session, reclaimed by the next publish's prune; process death drops every hold, which is correct because no container this process started outlives it without the boot reap. Three takers: the CLI invocation holds its pinned generation for the whole call (a call that resolves a generation the pruner has claimed is refused with "run the command again" rather than mounting a tree being removed); the service surface REPLACES its hold set wholesale each round, which is how a long-lived consumer's lease follows a refresh with no release call to forget; and publication claims the commit it is about to write — from BEFORE `install`, which clears `work/<sha>` before writing, through the rename that replaces the checkout's inode. Both of those last two are reachable by one route, a project pinning back to a version it recently ran whose generation a prune left in place *because* a consumer had it. Two things folded in rather than left beside: `dropSupersededVolumes` is GONE from the service path — removing a generation's volume is now part of taking the lease to delete the generation, and two sweepers racing on one volume name is the second mechanism this item exists to prevent — which also closes the recorded leak where a session refreshing without services accumulated one volume per refresh; and `retireForeignGeneration` drops the `active` link unconditionally (that is what the container follows) but takes the same lease over the trees. Review round (both confirmed at source, both fixed): the SERVICE hold was taken inside `ensurePluginVolumes`, which is **after** the awaited Docker round-trip that resolves the workspace volume's mountpoint — so a refresh could publish, claim, fully delete generation A and release its claim during that await, and the round would then hold a generation that no longer existed, re-create its work directories and build an overlay whose lowerdir was gone; the hold now happens in the same synchronous block that resolved the fragments, before the first await, which also closes the second finding (an in-flight round could add a hold *after* disposal had already run its one release, pinning a generation nothing uses). Two stated residuals: a refused prune does not retry on its own, so a session retains one generation per STILL-HELD generation — normally one, genuinely more when long invocations overlap several refreshes, and an earlier version of this item claimed a flat ceiling of one; and the prune derives volume names from the directories it finds, so a volume whose directories a DIFFERENT actor removed (disk-tier eviction wipes the whole state dir) is invisible to it — it holds no bytes, the boot reap drops every plugin overlay volume, and re-adding a Docker-listing sweeper to catch it sooner is exactly the second owner this lease replaced. **The one live-mount deletion no lease can cover, half fixed here:** teardown removes `workspace/` and `state/` outright (`reclaimRegenerableSessionDirs`), so it never asks anyone. The companion-CLI half is closed — the invocation's `isCancelled` promised in its comment that an ARCHIVED session stops the command and did not implement it, because `SessionManager.get` returns an archived row like any other, so only a deleted session cancelled anything. The rest is outside this slice and outside plugins: archive disposes the runner and does not await the asynchronous Compose stop before reclaiming, so a plugin service container can briefly outlive its own tree. Bounded — the session and everything in it are being destroyed — but it is the same defect class arriving from the one direction a lease cannot see
- [x] **The unguarded-reader class, closed where `active` is RESOLVED rather than in the wrappers** (merged in #2225). The wrappers took a required `expectedSource`, but `readGenerationRecordAt(dir)`/`readGenerationManifestAt(dir)` take no repository at all — so `plugin-cli-run.ts`'s `pinGeneration`, which resolves the link itself and then uses them, opted out of the check by construction, not by forgetfulness, and no compiler sweep over the wrappers could find it. It is also the worst place to miss: that directory is what the invocation container MOUNTS, so it feeds the entrypoint, the lowerdir, the volume name and `SHIPIT_PLUGIN_COMMIT` — every other unguarded reader displays or validates, and this one runs code. **Resolved by verifying at the pin, not by adding a parameter to the `…At` readers**: `readGenerationManifestAt` reads only the manifest and would have had to re-read the record its caller just read, on the path whose whole point is to read once. The `…At` readers keep their honest contract — *the caller has already verified this* — and the trade is stated rather than hidden: the check is a review-time shape there, not a build error. Four slices found this independently; the one that OWNED the path is the one that got the remedy right
- [x] **Session paths inside plugin containers are volume+Subpath mounts, never binds** — the per-session tree lives in a named volume in production (`container-lifecycle.ts` mounts workspace, credentials, uploads and scratch that way), so a plain bind of an orchestrator path silently yields an empty root-owned directory. It fails in PRODUCTION ONLY: dev and dogfood have real paths and look perfect. `install` sidestepped it because its one mount is a named volume, which needs no translation — which is why the existing plugin code gives no warning. Applies to `/project`, the state directory and the settings file on both the CLI and service surfaces. **A FILE subpath works** — settled from the daemon's source (moby @ 60eff6a) rather than by testing: `safepath.Join` bind-mounts "the exact same file/directory that was validated", and `tempMountPoint` (`daemon/volume/safepath/join_linux.go:102`) fstats the resolved fd and branches on `S_IFDIR` — a directory gets `MkdirTemp`, anything else gets `CreateTemp`, a regular file. Floor is API 1.45 (Engine 26); docs/263 already requires API 1.48.
