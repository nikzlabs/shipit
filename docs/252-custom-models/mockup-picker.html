Two selectors: harness, then model

Prototype for docs/252-custom-models. Today one dropdown lists models grouped by harness, because harness and provider are the same thing. Once they are separated, that grouping is wrong — the harness stops being a group and becomes an axis. This splits it into two selectors and lets you drive the result. The left panel is prototype scaffolding, not proposed UI — it stands in for what Settings and the deployment would decide.

req 3Model selection is still one place. Req 3 says every model is selected the same way in the same place — it says nothing about the harness, which is a different choice with different consequences. Splitting them keeps one model list while giving the harness the affordance it actually needs.
docs/138This is the real argument for the split: the lock. Per-agent credential isolation pins the harness for life after the first turn, while models stay switchable (req 4). Today that shows up as greyed-out rows scattered inside one model list, with a lock badge on a group header — you have to open the menu and read it to find out. Two selectors make it structural: one control is disabled with the reason on it, the other is fully live.
Toggle Has taken its first turn. In the combined picker this state is legible only from inside the dropdown; here it is visible on the closed composer.
The picker states what you choose on, and nothing else. No labels on the triggers, no API style, no explanatory footers. Each harness row gives its model count — the same information as the style, in the form the decision actually needs. Styles stay on Settings → Harnesses, whose entire job is explaining why a service appears under one harness and not another.
The service pill is the one conditional element: it appears only when the same model id is offered by more than one credentialed service on this harness — the single case where the id alone cannot say who is billing you, and the reason models are identified by the pair. Give OpenRouter a key while on deepseek-v4-flash and it appears; take it away and it goes.
req 11No persistent attribution strip. An earlier version of this prototype carried a “Running model via service on harness” row under the composer. It was cut as redundant: the two triggers already show the model, its service and the harness, and the model menu’s group headers already carry the billing kind. Req 11 asks that the user can tell, not that it is restated permanently.
“What actually ran” keeps its existing home in the usage modal (UsageModal.tsx, which already shows a Model stat) — that is where service and billing kind should join it, rather than in new composer chrome.
req 6The model list is the harness’s style joined against your credentials. Switch to Codex with only a DeepSeek key and you get one model, not two — the service speaks both styles but declares only deepseek-v4-flash under openai-responses. The grouping is by service, because that is what decides the credential, the price and the billing pill.
req 14Uninstalled harnesses are absent, not greyed. Cursor appears in the harness list only once the deployment installs it. Being installed is a precondition of the credential rule, not an exception to it — so the two knobs compose: no install means no models whatever your keys.
Entries are pairs, not model ids. Give OpenRouter a key and deepseek-v4-flash appears twice, under two services, at two prices. One list of bare model ids could not express that; two rows under two group headers can. Add Vercel too and it is three.
req 15The gateways are catalogue rows, not a feature. OpenRouter and Vercel AI Gateway are in the list because req 15 says the shipped catalogue must contain them — nothing in this prototype treats a gateway differently from DeepSeek. If a gateway needed special handling here, the service abstraction would be wrong.
Their declared styles are illustrative. Which styles each gateway really speaks, and which models under each, is research to do when the catalogue row is authored (req 6).
The other harness’s models are one control away, not lost. The combined picker showed everything at once and greyed what you could not have — worse as a lock affordance, better as a map. The obvious patch was a footer on the model menu (“3 more models on Codex”), and it was wrong: it grows with every installed harness, and it is useless the moment the harness is pinned, which is most of a session’s life.
The harness menu already answers it, on the control that would act on it: each row states its own model count. Open the harness selector — Claude Code · 5 models available, Codex · 3 models available. That does not grow into clutter, because it is one line in a menu that lists harnesses anyway.
openSwitching harness can strand the selected model. The prototype keeps the model when the new harness also offers it (that is why deepseek-v4-flash survives a Claude Code → Codex switch) and otherwise moves to the first eligible model and says so. Silently landing somewhere else would contradict req 11; refusing the switch would make the harness selector lie about being enabled. This is the one interaction the split creates that the combined picker never had, because there the model and harness moved together by construction.
req 12Removing a credential strands a running session — and that is already the specified behaviour. Uncheck the service the session is on. Req 8 says its models stop being selectable, but the session is already on one, and unlike a retirement (req 13) there is no successor of the same service to move to. Req 12 answers it without needing a new rule: an API key does not fail over, so ShipIt stops and says so.
What the split adds is only where that shows up — a picker state you can see before you send, rather than a failure you discover by taking a turn.
