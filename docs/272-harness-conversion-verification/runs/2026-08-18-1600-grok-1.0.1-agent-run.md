# Run — Grok Build 1.0.1, `shipit agent run` both directions (2026-08-18, outer)

Follow-up to [run 2026-08-18-1240](./2026-08-18-1240-grok-1.0.1.md), which
recorded this item as structurally blocked (no grok in the outer install, no
grok role). The operator redeployed the outer install with grok in its
harness set and created a grok-capable role; this run re-verifies those
preconditions and attempts the verification proper.

## Preconditions — cleared, verified 2026-08-18 ~16:00Z

- `shipit agent params` now lists **Grok Build (`--agent grok`)** with the
  xai/key models (grok-4.6, grok-4.3, grok-4.20 ×2) plus the gateway routes,
  and declares no reasoning levels (matching the docs/274 catalogue row).
  `/opt/shipit/agents/installed.json` in this session's container reads
  `{"harnesses":["claude","codex","opencode","grok"]}`.
- `shipit agent roles` lists **`Grok` — Grok Build · Grok 4.6 · Default**.

So both structural blockers from the previous run are gone, and the
explicit-target impossibility (no reasoning levels ⇒ no assemblable
explicit target) is moot: the sanctioned role path exists.

## INBOUND — Claude parent → grok sub-agent: FAILED (planning#442)

`shipit agent run --role Grok --prompt-file -` with a small bounded prompt
(read `package.json` fields + one arithmetic check), from this Claude-pinned
session. Two attempts, identical outcome:

| Run id | Result |
|---|---|
| `8d65173d-c5dc-4f8d-b264-2eb44bd97cd8` | `status: error`, `durationMs: 882`, `costUsd: 0`, no output |
| `91acc84f-800b-48fa-9709-ec5c1bb8ac95` | same (deliberate retry to rule out a transient) |

The routing half of the contract **worked**: the result JSON shows
`subAgentId: "grok"`, `roleName: "Grok"`, `runOn: {serviceId: "xai",
billingMode: "key", modelId: "grok-4.6"}` — the role resolved and the spawn
was admitted onto the intended harness/model/route. The process half then
died at CLI startup, which is planning#442, reproduced in this container
directly:

- `grok --version` → `@xai-official/grok: missing binary at
  /opt/agent-cli/node_modules/@xai-official/grok-linux-x64/bin/grok`; on
  disk only the compressed `bin/grok.br` (46 MB) exists — the image-build
  `npm rebuild` installed the real binary into the build user's
  `$GROK_HOME`, invisible at runtime.
- `~/.grok` is the image's symlink to `/credentials/.grok`, and no grok
  provisioning has created that target, so the link **dangles**;
  `fs.mkdirSync` through a dangling symlink throws `ENOENT` (verified
  empirically in-container), which defeats both the adapter's
  `makeSpawnHome` (falls back to the dangling real root) and the
  trampoline's own `$GROK_HOME/bin` bootstrap; its last-resort in-place
  decompress then fails on root-owned `/opt/agent-cli`. Exit 1 in under a
  second, zero stream events — all consistent with planning#442's
  diagnosis.

**planning#438 reproduces on the consult surface**: the run card /
`shipit agent result` show only `error` — "that run produced no output" —
with the CLI's actual stderr surfaced nowhere. Noted on planning#438 as an
additional sighting (the startup-death silence is not specific to the main
turn path).

## OUTBOUND — grok parent → Claude sub-agent: UNREACHABLE (same defect)

The defined form first: a one-shot sub-agent cannot itself spawn
(`/shipit-docs/agent.md` — "No recursion"), so the only grok-parent context
`shipit agent run` can be exercised from is a **grok-pinned session**. Spawned
one: child session `556b60ca-b238-4138-ba98-4d0f5413ea77` via
`shipit session create --role Grok`, prompted to run
`shipit agent run --role Fable` (Claude Code · Fable 5) with a bounded probe
prompt and echo the run id/exit/output.

Resolution again worked — `shipit session view` reports the child resolved
to `agent: grok, model: grok-4.6` from the role. The child then reached
`status: error` without producing a turn: the same planning#442 startup
death, now on the ordinary session-turn path of the outer install. The
outbound consult therefore never got to execute; nothing about the
grok→other-harness credential window was exercised or disproven.

## New defect found while tracing the spawn path

**planning#443** — `readSessionAccountMarker`
(`session-credentials-scaffold.ts:157`) filters marker keys through a
hand-written `claude|codex|opencode` list, so a marker written for `grok` is
unreadable by every consumer (identity check, write-back gate) and
self-erases on the next write. Latent while grok is key-only; breaks the
planning#435 subscription work when it lands. The planning#432 / docs/274
Phase 5 "silent sites" class — this site was missed by that sweep.

## Verdict and what re-arms this item

The docs/274 checklist box stays **unchecked**, now blocked on
