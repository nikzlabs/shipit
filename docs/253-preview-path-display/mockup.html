Preview toolbar — showing the current path

Path + query string only, no host or port. The host is noise: it's a generated subdomain like a3f9c2--5173.localhost that tells the user nothing. The route is the part that answers "where am I, and did the refresh keep me there?"

1 · Placement

The toolbar is a justify-between row that's already carrying a port selector, a device selector, an auto-fix toggle and three buttons.

Its own region, left-aligned Chosen

The path claims the slack between the two existing groups, so it truncates on its own terms and never squeezes the port or device selectors. But the content is left-aligned, not centred: the path starts at a fixed x position, so it stays where your eye last found it instead of sliding around as the route changes length.

2 · Long paths — what gets sacrificed

Query strings are long and the route is what you actually read. So the path holds its ground and the query gives up space first, rendered dimmer as a second-class citizen. Compare with the naive single-string ellipsis, which eats the route.

3 · States

  • Root — plain /, dimmed. Present but not shouting.
  • Unknown — nothing rendered at all. A non-proxied local preview has no injected script to report from, and an empty box would read as "the page has no URL".
  • Hover — full URL including host in the tooltip, click copies it. The host isn't gone, it's just not on screen by default.

4 · Where the value comes from

The iframe is cross-origin, so the parent can't read its location — the path has to be reported out of the page by the injected preview script, over the same shipit-preview channel that already sends loaded. A load-time read alone would go stale the moment the user clicks a link in an SPA, so the script also has to patch pushState/replaceState and listen for popstate. That's the one piece of real work here; the UI above is the easy half.
