
## Releases — how to cut a release

When the user asks to **cut / tag / publish a release** (e.g. "cut a 0.3.0 release", "release a patch", "tag an rc"), you are the actor that performs the mechanical steps. **Prefer the deterministic `shipit release` command** — `shipit release plan <bump>` (read-only: detect version + compute next, for the propose step) and `shipit release prepare <bump> [--pick <sha>…] [--from <branch>] [--bootstrap] [--prerelease [--confirm]]` (does the bump / branch / cherry-pick / PR or rc tag) — rather than hand-running git. ShipIt renders the result as an inline **release lifecycle card**. Read /shipit-docs/release.md for the full reference; the essentials:

**A release session is a special session — ShipIt owns its branch and you write nothing.** From the moment you run `shipit release`, two rules hold for the rest of the session. **Never change the branch:** `prepare` checks out `release/<version>` and leaves you there deliberately, and ShipIt resolves the session's pull request through the *checked-out* branch — move off it and the merge control for the release PR disappears, so the user can see the PR but can no longer merge it. Do not `git checkout`/`git switch`, and do not "restore" whatever branch you were on before. **And do not write any files** — no source edits, no doc updates, no scratch files: the post-turn auto-commit commits onto `HEAD` and the auto-push targets the checked-out branch, so anything you write is committed and pushed onto the open release PR, changing what merging it ships. **`RELEASE_NOTES.draft.md` (step 1b) is the one exception**, and only because it is gitignored — the auto-commit cannot pick it up, so the reason for the rule does not reach it. Run the command, report what happened, stop; if the user asks for unrelated work mid-release, say why it can't happen here and offer a separate session.

**First, determine the release mechanism.** Check `shipit.yaml` for a `release.mechanism` key:

- **`release-branch`** — releases are cut by **merging a version-bump PR into a maintenance branch** (`release.branch`, default `stable`); CI tags + publishes on merge. **You never push a tag.** This is the flow for this repo if `shipit.yaml` sets it.
- **`tag-triggered`** (the default when absent) — you push an annotated `vX.Y.Z` tag and the repo's own CI publishes the GitHub Release.

**1. Propose first — never act without confirmation.** Detect the version source in this priority order: `package.json` (Node, `version` field) → `Cargo.toml` (Rust, `[package].version`) → `pyproject.toml` (Python, `[project].version` or `[tool.poetry].version`) → top-level `VERSION` file. If `shipit.yaml` has a `release.version-source` key, use that instead. If **multiple** version sources are found (monorepo), surface the ambiguity in chat rather than guessing, and offer to persist `release.version-source` (and `release.version-source-path` for the path) in `shipit.yaml`. Compute the next [semver](https://semver.org) for the requested bump (patch / minor / major, or the explicit version the user named), and **propose** it. Do NOT bump, commit, tag, open a PR, or push yet. Emit a proposal marker on its own line so ShipIt shows the confirmation card:

```
<!--shipit:release {"action":"propose","version":"0.3.0","bumpType":"minor","tag":"v0.3.0","prerelease":false}-->
```

**The marker is the only thing that raises the card** — `shipit release plan` computes the version and raises nothing, so a turn that runs it without emitting the marker leaves the user no way to confirm. The marker carries **no notes field**: the card links to the draft (step 1b), because what publishes is that file and not anything you could restate here.

Then stop and wait. The card shows **Confirm & publish** / **Cancel**; the user confirms there (or replies "yes, ship it" in chat). A published tag and Release are outward-facing and effectively irreversible — this confirmation is the human-act gate.

**1b. Draft the release notes into `RELEASE_NOTES.draft.md` BEFORE you emit the proposal marker. This is REQUIRED, not optional.** On a repo whose release workflow publishes `.release-notes/<tag>.md` (ShipIt's own does — grep the workflow), a **final release never publishes GitHub's generated per-PR list**: `shipit release prepare` refuses a release with no notes, and CI fails the publish. There is no fallback to fall back to. Release candidates are the sole exception — an rc tags an existing commit and cannot carry a file, so it keeps generated notes.

There is one action, **Confirm & publish**, and confirming the release is also what accepts the notes — there is no separate "accept the notes" step to add, and the user need not have edited the draft for it to count as accepted. So the draft must exist **before** you emit the marker: on such a repo **ShipIt withholds the card entirely until it does**, so a proposal you make without one silently produces nothing. `shipit release plan` warns you when the draft is missing — read its output.

**Summarize what THIS release ships, which is not `stable..main`.** That range over-reports badly: the maintenance branch is squash-merged, so its release commits are unreachable from `main` and the range returns every commit since the branches diverged — including work already released. Instead: for `--from <branch>`, the work on that branch since the **previous release's** point on it (anchor on the previous release's version-sync commit on that branch, or on the previous tag's date, and say which you used); for `--pick`, exactly the commits being picked; for `--bootstrap`, the branch's content as a first release; for `--allow-empty`, say plainly that it ships no changes. Then write a **compact summary** — grouped highlights in the user's terms, not one line per commit or per PR. Write it as if it is the final text, because it is unless the user edits it. The card links to the draft, so the user opens it from there (or from the file tree) to read and edit it before confirming; because the file is gitignored their edit cannot dirty the tree `prepare` checks. `prepare` commits it as `.release-notes/<tag>.md` and CI publishes exactly that text, appending the Full Changelog link.

On a repo whose workflow does **not** consume `.release-notes/<tag>.md`, or that lacks the `.gitignore` entry, skip the draft entirely — there a stray file is all it would be.

**2a. On confirmation — `release-branch` repos: open a version-bump PR into the branch.** Run **`shipit release prepare <bump> [--pick <sha>…] [--from <branch>] [--bootstrap]`** — it creates the `release/<version>` branch off the maintenance branch, brings in the work (`--pick` for a hotfix, `--from` to bring a branch's content, `--bootstrap` for the first release), bumps the version source, and opens (or updates) the PR with base = the maintenance branch. You do NOT push a tag. **Merging that PR is the release** — on merge the repo's `release.yml` derives the tag from the merged commit, gates on a green build, creates + pushes the tag, and publishes the GitHub Release. You stop at the open PR; the user merges; CI does the irreversible publish. (Equivalent by hand only if the command is unavailable: `git checkout -B release/0.3.0 origin/stable` → bring in the work → bump the version source → commit → `gh pr create --base stable …`.) **Version-sync follow-up:** the version bump lands only on the maintenance branch, so the default branch (`main`) would drift behind every release. If the repo's `release.yml` opens a follow-up "Sync version to main" PR after publishing (ShipIt's own repo does), merge it to bring `main`'s version file in line — it touches only the version files. **To release `main`'s work, you MUST pass `--from main`** — a bare `prepare <bump>` with no `--pick`/`--from` brings no new commits and is refused as content-free (it would ship only the version bump); the error names the fix (`--from <branch>`, or `--allow-empty` for a deliberate bump-only release). **Cold-start caveat:** merge-publish only works once the merge-triggered `release.yml` (`on: push: { branches: [<branch>] }`) is on the maintenance branch — GitHub evaluates the workflow as it exists on the pushed branch. If the branch has no workflow or still has the legacy tag-triggered one, merging the bump PR runs **nothing** (no tag, no Release) even though the PR merges. `plan`/`prepare` print a **⚠ warning** when this applies — relay it and do NOT call the merge "the release"; the one-time fix is a tag-path release on a commit that already carries the merge-trigger workflow (or `--bootstrap` when the branch doesn't exist yet).

**2b. On confirmation — `tag-triggered` repos: bump, commit, tag, push.** First check idempotency: `git tag --list v0.3.0` and `git ls-remote --tags origin v0.3.0`. If the tag exists, emit `<!--shipit:release {"action":"already-released","tag":"v0.3.0","version":"0.3.0"}-->` and stop. Otherwise:

```
git add -A && git commit -m "Release v0.3.0"
git tag -a v0.3.0 -m "Release v0.3.0"   # annotated
git push origin HEAD
git push origin v0.3.0                    # triggers the repo's release CI
```

Then emit a tagged marker with the tag's commit SHA (`git rev-parse v0.3.0`):

```
<!--shipit:release {"action":"tagged","tag":"v0.3.0","version":"0.3.0","sha":"<full-sha>"}-->
```

**3. Never create the GitHub Release yourself.** Do NOT run `gh release` (it is blocked, by design). The repo's CI publishes the GitHub Release — from the merged bump PR (`release-branch`) or the pushed tag (`tag-triggered`). ShipIt polls for it and renders the published notes inline. For a `release-branch` repo, your job ends at the open PR; for a `tag-triggered` repo, at the pushed tag + the marker.
