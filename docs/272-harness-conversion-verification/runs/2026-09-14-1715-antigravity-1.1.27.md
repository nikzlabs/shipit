# Run — Antigravity 1.1.27, account mode (2026-09-14)

A follow-up to [the 10:50 run](./2026-09-14-1050-antigravity-1.1.27.md), which
ended **PARTIAL** with three named gaps. This run closes all three. It found no
defect in the harness; it did correct a *belief* the first run left standing —
that the subagent surface merely wanted a better prompt.

## Gap 1 — the subagent surface: measured on the wire

The first run asked for a subagent in the tour's step 7 and got a shell command
twice, which reads as prompt luck. It is not.

A prompt that names the tools and forbids the shell
([`subagent-prompt.txt`](../../301-antigravity-harness/probes/subagent-prompt.txt))
makes the model say so outright
([`subagent.ndjson`](../../301-antigravity-harness/probes/subagent.ndjson), exit
0, 11 s): *"I don't have access to the `define_subagent` or `invoke_subagent`
tools in my current environment."*

A model's account of its own toolset is a claim, so the answer comes off the
wire instead. `GOOGLE_GEMINI_BASE_URL` is redirected at
[`recorder.js`](../../301-antigravity-harness/probes/recorder.js) and the
outgoing `streamGenerateContent` body is read
([`tool-declarations.sh`](../../301-antigravity-harness/probes/tool-declarations.sh),
reproducible offline and against no quota — the recorder answers itself).

**The count was already on record and nobody had read it as an answer to this.**
The docs/301 tools-off probe of 2026-09-13
([`tools-off-1127.json`](../../301-antigravity-harness/probes/tools-off-1127.json))
captured the same **11** names, as the negative control for a different
question — *can anything empty this CLI's tool set?* — and its own README says
so. This run reproduces that number a day later, adds the configuration that
moves it, and draws the conclusion the earlier capture had sitting in it:

| Spawn | `init.tools` says | `tools[].functionDeclarations` carries |
|---|---|---|
| plain headless, `gemini-3.1-pro` | 57 | **11** |
| the same conversation **resumed** (`--conversation`, id verified equal) | 57 | **11** |
| `gemini-3.8-flash` | 57 | **11** |
| + one stdio MCP server | 57 | **14** (`call_mcp_tool`, `list_resources`, `read_resource`) |

The 11 are `find_by_name`, `generate_image`, `grep_search`, `list_dir`,
`manage_task`, `read_url_content`, `replace_file_content`, `run_command`,
`search_web`, `view_file`, `write_to_file`. Every name and every body size is in
[`tool-declarations.json`](../../301-antigravity-harness/probes/tool-declarations.json).

The resume matters because it is the configuration a reader would expect to
differ, and the first attempt at it **did not resume** — the conversation store
lives under `HOME`, so a fresh home quietly started a new conversation whose
declarations proved nothing. The script now reuses the first spawn's home and
prints both conversation ids so the reader can see they match.

**So `init.tools` is the CLI's catalogue, not the model's toolset**, and 43 of
the 57 are never offered in any of the four: the whole subagent family
(`invoke_subagent`, `define_subagent`, `browser_subagent`, `manage_subagents`),
every `browser_*`, the `ask_*` family, `command_status`, `send_command_input`,
`sed_file`, `multi_replace_file_content`, `notebook_edit`, `schedule`, `finish`.

Three consequences, and the first is the one that matters:

- The subagent surface is undrivable **by configuration, not by prompt**. Across
  a fresh turn, a resumed turn, a second model and an MCP-enabled spawn the tools
  are simply absent, which puts it in the same class as `ask_permission` and
  ends the first run's "no observed driver" as a question. **What this does not
  establish is version-wide impossibility**: every capture is key mode against
  the redirected `generativelanguage` endpoint, and an account-mode spawn talks
  to `cloudcode-pa.googleapis.com`, which this override does not redirect.
  Account mode's declarations are unmeasured.
- It retro-explains the `ask_question` capture: the model echoed the question in
  prose because it was never given the tool.
- Nine of the 18 names in `ANTIGRAVITY_TRANSCRIPT_TOOL_NAMES` did not arrive in
  any measured configuration. The map stays a superset deliberately — it costs
  nothing, and a later version that declares them renders a named card instead of
  a raw tool name.

**A gap this measurement exposes elsewhere.** ShipIt's review composer
(`src/client/utils/compose-review-body.ts`) falls back to *"spawn one fresh Task
subagent"* whenever Multi-agent is off or the brokered `shipit agent run` exits
non-zero. On this harness that instruction is undeliverable, because no subagent
tool is ever offered. The brokered path itself is proved (`probes/review.ndjson`),
so `supportsReview: true` stands; the fallback is a pre-existing mismatch this
run merely made visible, and it is not Antigravity-specific — it assumes every
harness has a native subagent. Filed as planning#571.

**The side call, with its purpose now read rather than inferred.** The
2026-09-13 endpoint-redirect capture already recorded a second, per-turn call on
`gemini-3.1-flash-lite-preview` that ShipIt never selects. This run reads its
body: for the one-word prompt measured, 819 bytes, **no** `tools` key, and a
system instruction that is a conversation-title generator. It fires on a NEW
conversation and not on the resumed spawn, which sent only its main request. The
stream's `usage` covers only the main conversation, so the call is invisible to
the harness's token accounting — on a model the user did not choose. How the
body grows with a real prompt was not measured; only the one size above is
observed.

## Gap 2 — Step 4 in full, on the ACCOUNT route

The dogfood inner instance, a real Google account
(`route=account:acct_bb68a5f5…`, `billingMode: "sub"`, `costUsd: 0`),
`gemini-3.1-pro-preview` at effort high, against
`nicolasalt-shipit/todo-list`.
[`account-spawn.log`](../../301-antigravity-harness/probes/account-spawn.log) is
the orchestrator's own lines for both turns — the route, `--add-dir <session
workspace>`, and `Google account token on disk — env credentials scrubbed so it
cannot be out-preferred`, which is the shape the 10:50 run fixed.

Two serial turns: the recipe's tour prompt, then one turn that asks for a
directory listing (the tour's own steps never force `list_dir`). Asserted on
persisted history
([`account-turn-history.json`](../../301-antigravity-harness/probes/account-turn-history.json)
— every tool call with its input and result summary, and the turn usage showing
`billingMode: "sub"`), then on the UI, then on the UI again after a reload.

| Surface | CLI tool | Transcript | UI card |
|---|---|---|---|
| File read | `view_file` | `Read`, `package.json`, `120 lines, 3862 bytes` | `Read package.json` |
| File write | `write_to_file` | `Write`, correct `file_path` | path + **no changes** |
| File edit | `replace_file_content` | `Edit`, correct `file_path` | path + **no changes** |
| Shell | `run_command` | `Bash`, stdout `conversion-probe` | `echo conversion-probe` |
| Search | `grep_search` | `Grep`, `pattern` + `path` | `Grep conversion-probe` |
| Directory | `list_dir` | `Glob`, real listing | `Glob` |
| Task list | — | no driver | — |

**Reload.** Both accessibility snapshots are committed —
[`account-ui-before-reload.txt`](../../301-antigravity-harness/probes/account-ui-before-reload.txt)
and
[`account-ui-after-reload.txt`](../../301-antigravity-harness/probes/account-ui-after-reload.txt),
236 lines each. They are **identical line for line** once element refs are
stripped, which the reader can check:

```
sed -E 's/\[ref=[a-z0-9]+\]//g' account-ui-before-reload.txt >/tmp/b
sed -E 's/\[ref=[a-z0-9]+\]//g' account-ui-after-reload.txt  >/tmp/a
diff /tmp/b /tmp/a
```

Rehydration from persisted history loses no card. (Stripping the refs is not
cosmetic license: Playwright re-mints them per page load, and the second load
also prefixes them `f1e…`, so a raw diff differs on every line that has one.)

The Write and Edit cards render as a path plus **"no changes"**. That is the
first run's known limitation seen from the UI side rather than inferred from the
stream: 1.1.27 puts only `TargetFile` in `tool_info.parameters`, so there is no
body and no diff to render. Upstream, not this branch.

**One environment caveat, and it is the dogfood's, not the harness's.** The
first tour turn read `/workspace/package.json` and wrote `/workspace/probe-note.md`
— ShipIt's **own** checkout — although the spawn's cwd and `--add-dir` both named
the session workspace. `prompts/skeleton.md` tells every agent *"You are running
inside a Docker container. The workspace is at /workspace"*, which is true in a
session container and false in local mode, where the clone lives at
`/workspace/sessions/<id>/workspace`. The model followed the prompt over its own
cwd. The stray file was removed; the second turn, told to use its cwd, addressed
the session workspace correctly. Nothing here is Antigravity-specific — any
harness can act on that line in the dogfood.

## Gap 3 — the negative control, both halves

The 10:50 run recorded its own control as weaker than the recipe asks for: the
vocabulary guard compared two constants, so it could not have caught a
fabricated name arriving in a *capture*. The recipe asks the control to flag
**the unmapped name AND the missing artifact**, which is the failure planning#337
actually was — a name the registry knew and no surface rendered.

`antigravity-tool-normalizer.test.ts` now has both checks over the committed
capture, and the control asserts both go red:

- `undeclaredToolNamesIn` — a captured name the registry does not declare.
- `untreatedToolNamesIn` — a captured name that reaches no transcript card, no
  MCP label, and no recorded decision to render it as itself. **Declaring a name
  does not silence this one**, which is the point: the control injects
  `TaskCreateV2` and it stays flagged even when treated as declared.

Each was proved red on its own: dropping `grep_search: "Grep"` from the
normalizer fails the treatment check, and stubbing the declaration filter to
return `[]` fails the control. The positive test also asserts the capture
carried more than five tool names, because an empty capture satisfies both
filters while checking nothing.
