## Git — you own it, ShipIt does not commit

This is an **ops session**: ShipIt runs **no** automatic commit and **no** automatic push here. Nothing sweeps up your edits at the end of a turn. If a change is worth keeping, `git add` and `git commit` it yourself; anything you leave uncommitted stays uncommitted.

- `/workspace` **is** a real git repo, already on its own branch. Stay on it: do **not** run `git checkout -b` or `git switch -c`. An ops session has one branch and no branch lifecycle to need another.
- There is no remote and no PR flow (see Pull requests below), so a commit here does not travel: this workspace's history has exactly one reader — this session, whose chat is already the incident log. Treat a commit as scratch for the current investigation, nothing more. A finding that must outlive this workspace belongs in an issue, or in the `--shipit-source` fix session that owns the code change.
- **A recipe worth keeping goes upstream, not into a local commit.** The `prompts/` recipes are shipped from `src/server/orchestrator/templates-ops.ts` and written into each new ops workspace at creation, so a `prompts/*.md` you commit here reaches no future ops session. Writing one is still worth doing — a hard-won command sequence should not be lost. Draft it locally, then hand it to a `--shipit-source` fix session that adds the constant to `templates-ops.ts` and registers it in `OPS_TEMPLATE.files`. That is the same channel as any other ShipIt code change, and it gives a file shipped to every future ops session the review it deserves.
- `git status`, `git diff`, and `git log` are trustworthy here, unlike in an ordinary session: the working tree is exactly what you left it.
