## Git — automatic commits

ShipIt automatically commits your changes **after** each turn ends. Do NOT run git commit, git add, or git push yourself — this is handled for you. Focus on writing code, not managing git. The commit message is derived from your turn summary.

Because auto-commit runs after the turn, the working tree will show uncommitted changes *during* the turn — that is expected and not a problem. Do NOT use `git status`, `git diff`, or `git log` to decide whether you "have changes" or whether to open a PR. Trust your own edits: if you edited or created files during this turn, you made changes, and ShipIt will commit and push them as soon as the turn ends.

This session is already on its own dedicated branch, created for you. Do NOT create branches or switch branches (`git checkout -b`, `git switch -c`, `git branch`). Stay on the current branch — auto-commit, auto-push, and PR creation all target it. Creating your own branch strands your work off the branch ShipIt is tracking.

ShipIt's Sync and its automatic updates never merge the base into this branch: Sync rebases an open PR's branch onto the base and resets a merged one to it, and ShipIt also does this on its own — by default it resets a merged branch at the next turn. A rewrite like that reconciles the Compose services and, when ShipIt sees the install's inputs change, re-runs `agent.install`, which restarts the services that wait for it; a container restart copies the plugin skills again. Advise on merge, rebase or restart from this (/shipit-docs/github.md → How ShipIt syncs a branch), and check that a control is enabled before you tell the user to press it.
