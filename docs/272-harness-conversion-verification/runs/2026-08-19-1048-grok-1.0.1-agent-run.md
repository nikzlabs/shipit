## Why the fallback produces case B

Traced statically and confirmed live:

1. Every session-worker image symlinks the credential root unconditionally —
   `ln -s /credentials/.grok /home/shipit/.grok`
   (`docker/Dockerfile.session-worker.prod:297`, `.dev:186`).
2. **Nothing ever creates `/credentials/.grok`.** Grok is key-only at launch
   (docs/274 req 6): credentials arrive as `XAI_API_KEY`
   (`shared/spawn-routing.ts`), no `auth.json` is ever written,
   `AGENT_CREDENTIAL_PATHS.grok = [".grok"]` copies from a source root that has
   no `.grok`, and there is no `POST_PROVISION_CONFIG` row for grok (only
   `claude`). Watching `/credentials` across a whole consult: no `.grok` ever
   appears.
3. So the link **dangles**. `fs.existsSync("/credentials/.grok")` is false while
   `lstat` reports a symlink.
4. `GrokAdapter.makeSpawnHome` (`session/agents/grok/adapter.ts:409`) opens with
   `fs.mkdirSync(realRoot, { recursive: true })`. Through a dangling symlink
   this **throws ENOENT** — reproduced directly:
   `ENOENT: no such file or directory, mkdir '/home/shipit/.grok'`.
5. The `catch` reads that as "could not build a per-spawn config root — fall
   back to the shared one" and `return realRoot`: **the very path that just
   failed**, now handed to the CLI as `GROK_HOME`.

The fallback's docstring calls this honest degradation — "a turn that runs
against the shared root might race a concurrent spawn over one file, while a
turn refused for a mkdir is no turn at all." That reasoning holds only when the
shared root *works*. Here the mkdir failed *because the root is unusable*, so
the fallback converts a repairable condition into a total turn failure whose
error names no cause.

## Why every earlier grok run was green

This is the part that reconciles today's failure with two green run docs.

The dogfood runs [2026-08-18-1240](./2026-08-18-1240-grok-1.0.1.md) and
[2026-08-18-1616](./2026-08-18-1616-grok-1.0.1.md) ran on the inner `dev`
service, built from `docker/Dockerfile.dev` — an image that creates **no
`.grok` symlink at all**. There `AGENT_HOME=/root` resolves `/root/.grok` as an
ordinary path, `mkdirSync` succeeds, and `makeSpawnHome` never reaches its
fallback. `Dockerfile.prod:137` *does* symlink `/root/.grok`, so the production
orchestrator in local mode is affected too. Green dogfood turns and a dead
outer consult are both true at once, and the image is the discriminator.

It also explains why planning#442 masked this: with no binary at all the
process died earlier, so this fallback never got to be the proximate cause.

## OUTBOUND — not reached

The defined form is unchanged from the previous run: a one-shot sub-agent
cannot itself spawn (`/shipit-docs/agent.md` — "No recursion"), so the only
grok-parent context `shipit agent run` can be exercised from is a **grok-pinned
session**, created with `shipit session create --role Grok`.

That was not reachable this run, for a reason worth recording precisely rather
than working around: `SUB_AGENT_PER_TURN_CAP = 3`
(`orchestrator/services/sub-agent.ts:97`), the budget refills only on a new
human instruction, and **`shipit session create` counts against the same
per-turn cap** (`services/child-sessions.ts:225`). The three inbound consults
consumed it, so both a fourth consult and a grok-pinned child session were
refused with `Sub-agent spawn cap reached for this turn (max 3)`. The same
refusal blocked the optional role-less explicit-target probe
(`--agent grok --service xai --billing-mode key --model grok-4.6`), which is
why docs/275's motivating acceptance case is unexercised here; the cap check
runs *before* target resolution, so a refusal yields no resolution evidence
either.

Independently of the cap, the outbound direction is predicted to fail the same
way: `makeSpawnHome` is called from `GrokAdapter.start()`, the single spawn path
for **every** grok turn rather than a consult-specific one, and `~/.grok`
dangles in every session container regardless of what the session is pinned to.
So an ordinary grok-pinned session turn should die identically at its first
turn. **That is a prediction from the shared code path, not an observation** —
it was not exercised, and confirming it is worth making the first step of any
planning#444 fix.

## Defect filed

**planning#444** — *Grok unusable in real session containers: dangling
`~/.grok` defeats `makeSpawnHome`, which falls back to the same dangling path
as `GROK_HOME`.* Carries the full diagnosis, the three-case controlled test,
and a two-part fix direction (materialize `/credentials/.grok` in key mode;
make `makeSpawnHome` refuse or route around a dangling root instead of falling
back onto it). It belongs to the same **key-only harness gets no credential
directory** class as planning#443 — one more site the docs/274 Phase 5
silent-sites sweep did not reach.

**planning#438 reproduces again**, and materially raised the cost of this run:
the CLI's stderr is specific and useful (`FS_OTHER / File exists (os error
17)`), and it reaches no surface at all — `shipit agent result` shows a bare
`error` with no output. Diagnosing it needed a process watcher, a
`/proc/<pid>/environ` grab and a hand-built controlled test.
