## Step 2 — inventories and registry diff (RED)

Extracted from both captures:

- **Event types:** `system` (subtype `init`), `assistant`, `user`, `result`
  (subtype `success`). All four have adapter cases (`grok/adapter.ts`
  `mapEvent`); nothing observed falls into `default: return null`. Layer A ✓.
- **Observed tool calls (9):** `todo_write`, `read_file`, `write`,
  `search_replace`, `run_terminal_command`, `grep`, `spawn_subagent`,
  `list_dir`, `get_command_or_subagent_output`. All are in `GROK_TOOL_NAMES`
  and `GROK_TOOL_MAP` ✓.
- **Input keys:** `todo_write{todos,merge}`, `read_file{target_file}`,
  `write{file_path,content}`, `search_replace{file_path,old_string,new_string}`,
  `run_terminal_command{command,description}`, `grep{pattern}`,
  `spawn_subagent{description,prompt,subagent_type,background}`,
  `list_dir{target_directory}`.

**Registry membership — the planning#337 check — fails on every surface
with a dedicated treatment.** The Codex/OpenCode adapters translate wire
names into the transcript vocabulary at Layer A (`codex-tool-normalizer.ts`,
`opencode-tool-normalizer.ts` per planning#432); the grok adapter has no
normalizer, persists raw names (its own conformance test asserts this), and
no recognition registry holds any of them:

| Surface | Driver observed | Registry check | Consequence |
|---|---|---|---|
| To-do / task panel | `todo_write` | ∉ `TASK_LIST_TOOL_NAMES` | no panel; `todos` default-dropped from the wire |
| File write | `write` (lowercase) | ∉ `DIFF_INPUT_TOOLS` (`Edit`/`Write`) | no diffStats, no green tint, `content` dropped |
| File edit | `search_replace` | ∉ `DIFF_INPUT_TOOLS` | no diff block; `old_string`/`new_string` dropped |
| Subagent | `spawn_subagent` | ∉ `SUBAGENT_TOOL_NAMES`/`SUBAGENT_REPORT_TOOL_NAMES` | no SubagentCall card; report body sliced away (`rendersResultContentInline` false) |
| Shell | `run_terminal_command` | `command` survives via the global `head` rule only | generic row/label |
| Read/search | `read_file`, `grep`, `list_dir` | not in `TOOL_ICONS`/activity switches | raw-text labels, `Using <name>...` |

Filed as **planning#437** (with the fix shape: a `grok-tool-normalizer.ts`
per the planning#432 precedent, guard-tested against the real registries).
Had the Step 4 matrix run, every row above would have failed in the DOM;
the offline diff caught it first, which is the recipe working as designed.

## Step 4, first attempt (~12:49Z) — blocked at the network boundary

Everything up to the wire works and was observed live in the dogfood
(`shipit service start dev`; grok baked into the dev image — boot logs:
"Harnesses installed by this deployment: claude, codex, opencode, grok";
`xai:key` credential adopted from `XAI_API_KEY` and seeded):

- `POST /api/sessions/headless {agent:"grok"}` accepted; env-prep resolved
  `route=reserved:env:XAI_API_KEY`; adapter logged
  `[grok] service routing: xai/key -> https://api.x.ai/v1` and spawned
  `grok --output-format streaming-messages-json --always-approve
  --no-auto-update -m grok-4.6 -s <uuid> --prompt-file …` — session-UUID
  pre-assignment on turn 1 and `-r <same-uuid>` resume on turn 2, both as
  designed (session `05a20654-9282-474c-9035-aa16bd395f91`).
- Every turn then died: `Error: Couldn't set model 'grok-4.6': Invalid
  params: "unknown model id"`, exit 1 — the CLI's `/models` preflight
  failing, phrased misleadingly. Root cause proven by direct probe from
  inside the dev container (via a DeepSeek-routed inner turn): `getent
  hosts api.x.ai` → rc=2, `curl https://api.x.ai/v1/models` → `000`, while
  `api.deepseek.com` → `401` (reachable). **The outer deployment's enforced
  egress allowlist predates the merge** — `api.x.ai` is in all three lists
  in the merged code (`egress-allowlist.ts`, `egress-firewall.ts`) but not
  in the running deployment; my own session container cannot resolve it
  either. Consistent secondary evidence: the outer install's
  `shipit agent params` lists three harnesses (no grok) and its
  session-worker image carries no `grok` binary.

**Billing-route canary (inconclusive, method recorded).** To prove the turn
bills the routed credential rather than the ambient `XAI_API_KEY` in the dev
container env (values are identical, so the bill alone cannot distinguish),
the stored `env:XAI_API_KEY` route was PATCHed to an invalid canary, a turn
run, the real value restored, and a control turn run. Both turns failed
identically — on the egress block, upstream of auth — so the pair proves
nothing about billing. The negative-control discipline (docs/272 / the
docs/274 vision-probe lesson) is what kept the canary's first "auth failure
confirms the route" reading from shipping as a conclusion. Mechanism
evidence that remains: the adapter's routed path scrubs
`XAI_API_KEY`/`GROK_AUTH`/`GROK_AUTH_PATH` and delivers exactly
`process.env[routing.credentialSourceEnv]` (`grok/adapter.ts`), and the
`service routing` log line above shows that path taken. The bill-side proof
needs a rerun once egress is open. Credential state was restored (route
`ready`, real value) before this doc was written.

**Transcript silence defect (planning#438).** Both failed turns persisted
no explanation: turn 1 an empty assistant row, turn 2 no assistant row at
all. The adapter's synthesized `agent_result {status:"error"}` sets
`lastTurnErrored` but never becomes a persisted row, and its existence
bypasses `onNoResultExit`'s retry-and-surface path.

## `shipit agent run` both directions — BLOCKED, structurally

- **Outer install:** grok is not in the deployment's installed-harness set
  (no spawn-inventory section, no binary), and independently an explicit
  target naming grok cannot be assembled at all — grok declares no
  reasoning levels and `SpawnTarget`'s `explicit` kind requires one
  (docs/274-grok-build-harness plan.md "one deliberate limitation"); the
  sanctioned path is a grok-based role, and none exists on this install.
- **Inner dogfood:** local mode installs no `shipit` shim at all
  (`Dockerfile.dogfood` — deliberate, planning#305), so `shipit agent run`
  does not exist there for any harness.

Same shape as the docs/268 OpenCode deferral ("needs a full dogfood
install"). Runnable once the outer deployment runs the merged code with
grok in `SHIPIT_HARNESSES` and a grok role configured — and worth running
only after planning#437 lands, since a consult's transcript rendering is
the thing being verified.

## Rerun after the network grant (same day, ~14:00Z)

The operator granted `api.x.ai` egress mid-run (Settings → Network), which
unblocked everything except the structural `shipit agent run` items. What
then ran, in order:

**Billing-route canary — now conclusive, PROVEN.** With egress open the two
arms finally differ only in the stored credential value. Canary arm: stored
`env:XAI_API_KEY` PATCHed to an invalid value → minimal grok turn (session
`a83b2d96…`) fails with the CLI's auth error ("Not signed in … set the
XAI_API_KEY environment variable", exit 1) — while the ambient
`XAI_API_KEY` in the same container's process env is the real, working key.
Control arm: value restored → the full tour turn succeeds. Therefore the
spawn's credential is the stored route's value delivered via
`routing.credentialSourceEnv`, not an ambient inheritance — the
`HARNESS_CREDENTIAL_VARS` scrub + single-delivery path works, and the bill
follows the credential store. Bill-side confirmation: the turn's persisted
usage row reads `model grok-4.6, billingMode "key", costUsd 0.124722`, and
the composer dial shows "Metered spend … $0.12".
